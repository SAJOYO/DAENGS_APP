# 서버 산책 일기를 앱에서 읽기

서버 [DAENGS_dev #378](https://github.com/SAJOYO/DAENGS_dev/pull/378)의
`walk-diary-response-v1` / `walk-diary-bundle-v1`을 산책 목록과 지도 위 장면에 연결한다.
새 경로는 `WalkDiarySync`, 이전 후보 계약은 `WalkStoryboardSync`가 맡는다.

## 요청과 복구

1. 기존 순서대로 GPS finalize → 행동·메모/위치 확정 → 사진 메타데이터 동기화를 마친다.
2. `GET /app/walks/storyboard/capabilities`에서 `diary_formats`를 확인한다.
   404 또는 빈 목록이면 기존 v2~v5 분석을 사용한다. 통신 오류나 새 형식 오류에서는
   구형 생성으로 바꾸지 않는다.
3. 새 형식을 지원하면 `GET /app/walks/{id}/storyboard?bundle_format=walk-diary-bundle-v1&target_scene_count=5`로 조회한다.
4. 결과가 없거나 stale/failed이면 같은 경로에 POST한다. `expected_entries`와
   GET에서 확인한 `expected_photo_manifest`를 함께 보낸다. 로컬 사진이 있으면 먼저
   ACK된 publisher/revision과 서버 manifest가 같은지도 대조한다.
5. 정상 캐시에는 POST하지 않는다. 명시적인 갱신은 `refresh=true`로 한 번 요청한다.
   `running`은 `refresh=false` POST 한 번으로 서버의 lease를 확인한다. 살아 있으면 재사용하고
   프로세스 종료 등으로 60초 lease가 만료됐으면 복구한다. 이후 최대 8번, 2초 간격으로
   조회하고 완료되지 않으면 WorkManager 재시도 흐름에 넘긴다.

목표 5장은 이번 연결의 기본 보충 목표다. 사용자 기록이 5개를 넘으면 모두 남고,
근거가 부족하면 5개 미만으로 남는다. 목록 페이지 크기나 LLM 호출 수 제한과 다르다.

## 저장과 최신성

Room 테이블이나 버전은 바꾸지 않는다. 기존 `walk_scene_analysis.bundle`에 새 응답
전체를 저장해 모델 상태·사진 버전·준비 진단을 보존한다. parser가 형식별로 분기한다.
`GeoStoryboardBundle`은 기존 화면 연결용 표현 모델이며 새 응답을 구형 wire JSON으로
변환하는 것은 아니다.

새 로컬 stamp는 `diary:` 접두사와 기록 stamp·사진 목록·사진 ACK 상태의 hash를 가진다.
저장 직전 DAO 트랜잭션에서 현재 계정·원본 stamp·generation을 다시 비교한다.
목록 제목과 지도도 사진 변경을 관찰하므로 삭제된 사진을 이전 일기로 되살리지 않는다.
옛 stamp는 이전 알고리즘 그대로 읽는다. 사용자 편집과 검토 사본은 별도 테이블에 유지한다.
편집 JSON의 `body_scope=SCENE`은 장면 전체 본문을 뜻한다. 필드가 없는 이전 사본은
`SOURCE`(원본/배경 문구 편집)로 읽고 기록 재료를 이어 붙인다. 전체 본문 편집은 빈 문자열도
그대로 복원하며 재생성 결과나 원본 메모를 뒤에 다시 붙이지 않는다. Room 스키마 변경은 없다.

생성 실패와 모델 문장 실패는 다르다. 서버가 `ready`와 `model_status=unavailable`을
반환하면 원본 장면을 보여주고 배경 문장 실패를 안내한다. 강제 갱신 전까지 자동으로
LLM을 반복 호출하지 않는다. 일반 일기 화면에는 별도 검토 완료 단계를 두지 않는다.
이전 실험용 검토 화면의 최신성 판정과 저장 사본은 호환성을 위해 유지한다.

## 화면과 원본

- 산책 목록의 제목은 서버 일기 제목이며 개별 장면 제목은 기록 종류에 따른 앱 표제다.
- 탐색 상태에서는 산책 제목을 독립된 줄에 26sp 굵은 글씨로 표시하고 지도를 넓게 쓴다.
  장면을 고르면 아래 카드가 올라오고 상단 산책 제목은 한 줄로 줄어든다.
  카드를 아래로 끌거나 '장면 목록'을 누르면 선택을 해제하고 지도 중심 탐색으로 돌아온다.
- 장면 제목은 22sp, 목록 제목은 18sp, 본문은 20sp / 줄 높이 30sp다.
  긴 본문만 스크롤하고 이전·다음 이동은 카드 아래에 고정한다. 다음 장면은 제목부터 연다.
  목록 스크롤 위치는 장면을 읽고 돌아와도 보존한다.
- 생성·갱신과 기록 추가는 상단 더보기 메뉴에서 연다. 지도 색상 설정은 지도 위 버튼으로 유지한다.
- 지도 인스턴스를 유지하고 카드 목표 높이만큼 SDK의 아래쪽 가림 영역을 갱신한다.
  일기에서만 선택 위치를 보이는 지도 영역 가운데로 유지하며, 선택을 해제하면 전체 경로로 돌아온다.
  헤더 높이 변경 후 실제 지도 크기로 다시 맞추고, 순번·출발/도착과 설정 버튼을 위한 여백을 둔다.
  패딩 변경은 `keepCameraTarget=true`로 적용해 SDK의 추가 중심 이동과 명시적인 경로 맞춤이 겹치지 않게 한다.
  지도 공급자의 `keepSelectionVisible` 옵션은 기본 false로 다른 화면의 카메라 동작을 유지한다.
- 목록과 장면 제목 옆 연필에서 같은 장면의 제목·본문 전체를 수정한다. 카드 안에는
  하나의 본문과 하나의 편집 동작만 있다. 원본 기록용 구획·연필은 두지 않는다.
  별도 스토리보드 검토 버튼은 일반 화면에서 제거한다.
- 장면 수정은 현재 계정의 완료된 세션인지 확인한 뒤, 트랜잭션에서 최신 초안에 해당
  장면만 합쳐 저장한다. 기존과 같은 기기 내 편집이며 서버 업로드 기능을 추가한 것은 아니다.
  재생성 시 수정 문구를 유지하고 원본 fingerprint 변경을 표시한다.
- 정상 생성에는 장면 수 부족이나 생성 정책을 설명하는 문구를 붙이지 않는다.
  실패·재시도 상태는 안내하며 내부 진단의 부족 장면 수는 계속 보존한다.
- 서버의 배경·행동·메모·사진 재료는 `sceneBody()`에서 하나의 본문으로 조립한 뒤
  `DiaryScene.body`로 넘긴다. 읽기 화면과 편집창은 이 본문을 그대로 사용한다.
  LLM은 같은 보드의 초안을 채우며 사람은 그 장면 전체를 고친다. 구조화된 생성 출력은
  내부 처리 계약이고 사용자 화면의 구획이 아니다.
- 행동 코드는 본문 속 행동 문장으로, 사진은 사진을 남긴 문장으로 표시한다.
  기기 이동 관측은 관측된 이동만 서술하며 동물의 행동·원인·의도를 덧붙이지 않는다.
  메모의 줄바꿈과 공백은 조립 시 보존한다. 수정 본문 상한은 원본 메모 2000자와
  생성 문장을 함께 담도록 4000자다. 원본 메모·행동 코드·사진·지도 위치는 바꾸지 않는다.
- `직접 남긴 기록`·`이동 기록` 소제목, 구분선, 별도 기울임, 위치 판정 출처는 카드에
  표시하지 않는다. 장면 시각과 명시적 동 주소는 제목 아래에 함께 표시한다. 현재 서버의 주변 시설 공급자는
  아직 동/공원/하천의 상세 관계를 공급하지 않는다.
- 행동·사진은 서버가 반환한 위치 방법을 유지한다. 추정/마지막 위치를 관측 GPS처럼
  표시하지 않는다. 체류·속도 장면은 기존 원본 GPS 순번·시각·chain 대조를 통과해야 지도에 찍는다.
- 사진 ID는 기기 파일과 연결한다. 이미 서버 장면에 포함된 사진을 별도 카드로 다시 추가하지 않는다.
  숨김도 유지한다. 다른 기기에는 사진 파일이 없을 수 있어 촬영 기기에서 볼 수 있다고 안내한다.
- 지도 핀 안의 숫자는 장면 순서다. 같은 위치의 여러 장면은 각 순번을 함께 표시한다.
  같은 좌표에 4개 이상 있으면 첫 두 순번과 선택 순번, 생략 표시를 사용한다.
  전체 순번과 각 장면은 원본 모델·목록에 보존하며 밀집도 숫자로 바꾸지 않는다.
- 일기에서는 출발·도착을 작은 글자 표식으로 좌표 아래에 표시하고 장면 핀은 좌표 위에 표시한다.
  장면 핀과 1m 이내에서 겹치는 체류 그림만 표시 단계에서 생략한다.
  체류·GPS 원본과 다른 지도 화면의 기존 그림은 그대로 유지한다.

## 검증 자료와 범위

`app/src/test/resources/storyboard/diary-v1.json`은 Dev 커밋
`f3b18bf3d2f60ac4ec63a26cc45238817a64b6bf`의 합성 record/observation 재료를
`prepare_stamps` → `assemble_diary` → `DiaryStoryboardResponse`로 검증·직렬화한 응답이다.
문장은 고정된 가짜 writer 응답이다. 실제 Gemini 호출이나 실제 사용자 산책 데이터가 아니다.
메모·행동·체류·사진을 포함하며 목표 5개 중 4개만 준비된 경우다.

타겟 검증은 새 parser/Room 동기화·기존 후보 호환·일기 투영·목록 reader·지도/검토
Composable을 다룬다. 명령과 실행 결과는 이 작업 PR의 `확인한 것`에 기록한다.
새 Composable에는 Preview를 제공한다.

글자 크기·인라인 편집 변경에서는 지도 UI, 초안 저장, parser, reader, 기존 검토 화면
5개 클래스의 31개를 실행했다. 30개는 통과했고 입력창 테스트 1개가 기존
`WalkEntryEditorTest`에 기록된 Robolectric AlertDialog/TextField idle 문제로 실패했다.
같은 슬롯 방식으로 창과 입력 동작을 분리한 뒤 지도 UI·parser 2개 클래스의 16개가
모두 통과했다. 여기에는 새 로컬 사진 편집·숨김 검증 1개도 포함된다.
디버그 빌드도 성공했다. 폰의 별도 확인 앱 업데이트 후 설치 APK와 빌드 결과의
SHA-256을 대조했다. 실제 터치로 제목·본문·스크롤과 두 편집 다이얼로그 표시를
확인했으며, 육안 확인 중 기록을 변경하거나 저장하지 않았다.

2026-09-09에는 앱 `00d75c29`와 서버 `f3b18bf3`로 별도 로컬 종단 검증도 수행했다.
에뮬레이터 합성 GPS 48개와 행동·메모·사진 각 1개를 실제 저장·HTTP 동기화 경로로
전달했다. 실제 Gemini 호출은 1회, 모델 시간 3.735초, 입력 911 / 출력 141토큰이었다.
서버 제목과 배경 2개를 포함한 장면 3개가 앱 캐시와 지도에 표시됐고, 재시작 후
조회에서도 generation 1을 유지했다. 선택 계측 `WalkDiaryLiveTest#resumeSavedWalk`는
1개 통과했다. 원본 보고서·입출력은 로컬 워크스페이스의 `outputs/diary-e2e`에 보존했다.

이 종단 검증은 실제 사용자 산책이 아니다. Place는 카페 40m 응답 fixture, 사진은
합성 JPEG이며 AVD mock 표식은 localhost 전용 계측 어댑터에서 정규화했다.
실제 GPS 품질·촬영 UI·공공데이터 공간 정확도 검증과 구분한다.
실기기에는 이 결과를 담은 별도 오프라인 확인 앱을 설치했으며 기존 스토어 앱은 유지했다.
서버 기능 `DAENGS_WALK_DIARY_ENABLED`는 기본 false다. 공유 서버 배포·활성화는
수행하지 않았고 로컬 검증 서버는 종료했다.

지도·카드 읽기 구조 개편은 지도 UI·기존 스토리보드 UI·지도 표시 정책·출발/도착
4개 클래스의 26개 테스트가 통과했다. 이후 SDK 카메라 보정은 debug 빌드와
Samsung SM-S931N의 별도 확인 앱에서 검증했다. 핀으로 장면 선택, 이전·다음 이동,
카드를 끌어 내려 전체 동선 복귀, 제목·배경 및 원본 기록 편집 창 표시를 확인했다.
편집 창에서는 저장하지 않았다. 출발·도착과 순번 배지가 카드·지도 버튼에 가리지 않는지
합성 산책에서 확인했으며, 다양한 실제 산책의 길이·밀도 검증까지 포함하지는 않는다.

이후 본문 통합 작업에서는 본문 조립·이전 사본 호환·전체 본문 저장/재조회·재생성 후
수정 보존과 UI를 다루는 6개 클래스 42개 테스트가 통과했다. 같은 폰 확인 앱에서
하나의 본문과 연필 하나가 표시되고 편집창에 그 본문 전체가 들어오는 것을 확인했다.
설치 APK 해시를 대조했으며, 이 작업에서 새 LLM 호출이나 원본 메모 수정은 하지 않았다.
