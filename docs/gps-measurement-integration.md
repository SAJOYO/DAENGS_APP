# GPS 거리·경로·완료 기록 연결 (#319, 5-2 전환)

새로 시작한 산책은 저장된 이동 정책으로 거리·경로·활동 시간을 계산한다.
실시간 서비스와 완료 후 재생이 같은 엔진·경로 투영기를 사용한다. **신규 행동 핀은 v1**이며
실측 위치 자격·원본 번호·기존 전송 경로를 유지한다. 서버 계산 전환은 구현하지 않았다.

## 어떤 산책부터 바뀌는가

`openSession`이 `MotionPolicies.freeze(..., measure = true)`로 정책을 동결하고,
기존 envelope에 `measurementVersion: motion-measurement-v1`을 넣는다.
Room 16의 `motionPolicyJson`을 사용하므로 추가 DB 이관이나 개발자 설정은 없다.

| 저장된 정책 | 완료 거리·경로·시간 |
| --- | --- |
| 정책 없음 | 기존 `summarizeLegacy` |
| #313의 4필드 정책, 측정 버전 없음 | 기존 계산 유지. 정책이 있다는 이유로 소급 전환하지 않음 |
| 지원하는 측정 버전 | 당시 설정과 원본·완료 epoch를 재생 |
| 손상·미지원 정책 또는 불완전 측정 원본 | 명시적 실패. 현재 기본값·0m·기존 계산으로 대체하지 않음 |

진단용 `compareMotion`의 비교 기준은 계속 명시적인 legacy 계산이다.
설정 해시는 설정 JSON만 식별한다. 정책·관측·측정 버전도 함께 비교해야 한다.

## 실시간과 완료의 공통 계산

- Room에 확정한 원본을 접수 번호 순서대로 엔진에 전달한다. 원본과 핀 참조는 재번호하지 않는다.
- `MotionTrail`은 엔진의 `START_NEW/CONTINUE/SKIP` 결정을 그린다. 두 번째 거리 필터를 만들지 않는다.
  고속 제외·재진입·일시정지·긴 공백 뒤 구간을 잇지 않는다. 표시 속도를 적분하지 않는다.
- 실시간 경로는 최대 5,000개 점을 유지한다. 오래된 점을 덜 그려도 엔진의 전체 거리와
  최초 출발점을 보존한다. 완료 요약의 기본 제한도 같다. 단일 산책 상세와 목록 썸네일의
  기존 전체 경로 읽기/축약 방식은 유지한다.
- 시간은 활성 기록 epoch 길이의 합이다. 첫 GPS 대기·기록 중 정지도 포함하고 일시정지는
  제외한다. 따라서 실제 보행 시간이라고 해석하면 안 된다. GPS가 없으면 거리 근거는 생기지 않는다.
- PAUSE/STOP 게이트가 닫히면 즉시 시간을 고정하고, 저장된 꼬리를 처리한 뒤 실제 종료 경계를
  엔진에 전달한다. 일시정지 후 종료의 빈 STOP은 0초를 더한다.
- 새 측정 버전에서 종료와 같은 단조 시각의 점은 종료 번호 장벽 전에 접수된 경우 포함한다.
  `recordingEligible` 및 수신 시각을 검증한다. 이전 비교 정책은 기존 반열린 구간 규칙을 유지한다.
- 완료 경로의 시간축은 단조 시각에서 일시정지 시간을 뺀 값이다. 벽시계가 바뀌어도 점의
  활동 시점과 구간 속도가 거꾸로 가지 않는다. 원래 촬영 시각은 따로 보존한다.

서비스 완료 화면, `WalkHistory`의 목록·합계·상세, `RoomWalkRecordsSource`, 로컬 일기 준비가
같은 `summarize`를 사용한다. 일기 준비에서도 속도·source·clock 등 원본 메타데이터를 보존한다.
일기·기록을 조회할 때 옛 산책을 새 정책으로 다시 쓰지 않는다.

완료·재시작 복구의 60초/50m 판정도 해당 세션의 요약을 사용한다. 기존처럼 행동·사진 기록이
있으면 짧은 산책도 보존한다. 미지원 정책이나 결손 원본은 복구 과정에서 짧은 산책으로 삭제하지
않는다. 라이브 계산 오류는 원본 저장을 막지 않고, 완료 결과는 저장 원본의 재생으로 확인한다.

## 서버 전달 후속 계약

후속 구현: DEV #449가 독립 백업 capability·부속 저장·완료 검증·읽기를 제공하고,
APP #325가 [전송·재시도·검증된 복원](gps-motion-sync.md)을 연결한다.
아래는 최초 설계와 당시 서버 상태이며, 서버의 동일 정책 계산은 계속 후속이다.

2026-09-11 DEV `c27890eb`의 `schemas/walk.py`, `services/walk_finalize.py` 기준:
기존 업로드는 좌표·벽시계·chain·정확도·mock·nullable `recording_eligible`를 받는다.
단조 시각·수신 시각·속도/방향 품질·source/clock·epoch·정책 envelope 전체는 받지 않는다.
서버는 별도 `WalkEvidencePoint`로 거리·시간을 계산한다. 따라서 현재 앱의 측정 결과와
서버 분석·모아보기 결과가 같다는 보장은 없으며, 서버에서 새 기기로 복원한 기록은 legacy다.

다음 서버/앱 연결 단위는 아래를 함께 구현·검증해야 한다.

1. **독립 capability:** 예를 들어 `gps-motion-measurement-v1` 지원 여부를 인증된 계약으로 확인한다.
   기존 `gps-recording-v1`이나 v2 핀 지원을 같은 의미로 취급하지 않는다.
2. **원본 부속 저장:** 기존 raw 점 번호에 source/clock, 측정·수신 단조 시각과 수신 벽시계,
   속도/방향 및 각 품질·provider·eligibility를 대응한다. epoch에는 시작·종료 단조/벽시계,
   chain, 첫/끝 번호, 개수, 종료 종류와 drain/실패 증거를 보존한다. int64 시각을 손실 없이 받는다.
3. **동결 정책:** 최초 세션의 버전·관측 스키마·측정 버전·정확한 설정 JSON·설정 해시를 저장한다.
   서버가 업로드 시점 기본값을 덧씌우지 않는다. 지원하지 않는 정책은 사유와 함께 보류한다.
4. **별도 증명:** 기존 raw fingerprint를 바꾸지 않는다. 부속 원본·epoch·정책을 묶는 새 digest의
   정렬, null과 결측, 숫자 인코딩을 양쪽 계약에 고정한다. 서버는 기존 raw 번호와 개수까지 대조한
   영수증을 반환하고, 앱은 이 증명을 받은 뒤에만 측정 백업 완료로 표시한다.
5. **재시도와 소유권:** 같은 세션·digest 재전송은 멱등이며 다른 내용 덮어쓰기는 거절한다.
   부분 업로드·오프라인·응답 유실·계정 전환에서 기존 raw/핀 대기열을 소실시키지 않는다.
6. **서버 계산과 복원:** 지원 정책을 서버에서 동일하게 재생한다. 로컬 수치만 신뢰해 확정하지 않는다.
   동일 fixture의 각 구간·제외 이유·최종 거리/시간을 양쪽에서 비교한다. 정책·원본·epoch·영수증
   전체를 검증한 복원만 새 reader로 읽으며, 일부만 복원한 것을 완전한 측정 기록으로 승격하지 않는다.
7. **배포 순서:** 서버 저장/검증/복원 지원을 먼저 배포해 확인하고 앱 전송을 연결한다. 미지원 서버에는
   기존 raw/핀 전송을 유지하면서 측정 부속 백업을 대기로 남긴다. v2 핀 활성화는 별도 변경이다.

공통 재생 사례는 고속→정지→보행, 위치/속도 품질 불일치, 배치 수신, 일시정지와 빈 STOP,
같은 시각 종료, 벽시계 변경, 결손/미지원 정책, 60초/50m 경계다. 기존 eligibility 영수증만으로
새 측정 백업 완료를 판정하는 구현은 완료 조건을 충족하지 않는다.

## 검증 범위

기존 테스트 클래스에 채택/legacy·종료 경계·경로 상한·단조 시간축·재시작 사례를 추가한다.

v1 핀 생성, 완료 재생의 일치를 확인한다. 파일 DB 재개방 후 목록·상세·기록 선택·일기 준비도
