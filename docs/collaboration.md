# 협업 규칙

2026-08-22 협업 특강(이동규 멘토)에서 가져온 기준이다. 원본은 백엔드 저장소
[`SAJOYO/DAENGS_dev`](https://github.com/SAJOYO/DAENGS_dev) 의 `docs/collaboration.md`
에 있고, 이 문서는 그것을 **앱 저장소에 맞게** 옮긴 것이다. 절 번호와 제목은 일부러
맞춰 두었다 — 같은 규칙을 두 저장소에서 찾을 때 같은 자리에 있어야 해서다.

저쪽에만 있고 여기 없는 것: 배포 파이프라인, 서버 상태, DB. 앱은 머지해도 아무 데도
배포되지 않는다. 그 자리는 **에셋과 실기기**가 대신한다 (7절).

PR 본문 양식은 [`.github/PULL_REQUEST_TEMPLATE.md`](../.github/PULL_REQUEST_TEMPLATE.md),
코드 규칙은 [`CLAUDE.md`](../CLAUDE.md), 되돌리기 번거로운 결정은
[`HISTORY.md`](../HISTORY.md) 에 있다.

## 1. 역할 — 사람은 앞단과 뒷단에만

사람은 in the loop 가 아니라 **on the loop** 에 있다. 앞단(무엇을 먼저 할지)과
뒷단(나온 결과가 유효한지)만 사람이 잡고, 그 사이는 AI 에게 맡긴다.

| 사람이 정하는 것 | AI 에게 맡기는 것 |
| --- | --- |
| **우선순위** (P0 / P1) | 프로덕트 백로그 쌓기 |
| Iteration 기간 | 태스크 쪼개기, PR 작업 목록 작성 |
| **결과물이 유효한지 검증** | 구현 · 커밋 · PR 본문 작성 |
| **작업이 섞이지 않았는지 확인** | 커밋 메시지 · PR 메시지 |
| **그림이 예쁜지 · 화면에서 제대로 보이는지** | 좌표 계산 · 배치 로직 · 테스트 |
| 실기기 상태 (뭐가 깔려 있나, `adb` 인증이 살아 있나, 지금 폰을 쓰고 있나) | 빌드 · 설치 명령 |
| 저쪽 아트 저장소와의 조율 (뭘 다시 그려 달라고 할지) | 받은 것을 반입하고 검증 |
| **회고** | — |

**우선순위는 AI 에게 위임하지 않는다.** AI 는 검증에 과몰입하고 가끔 산으로 간다.

**그림 판단도 위임하지 않는다.** 테스트는 좌표가 맞는지는 잡아도 강아지가 귀여운지는
못 잡는다. 실기기에서 사람이 본다.

## 2. 우선순위 (P0 ~ P3)

Project 의 `Priority` 필드에 쓴다. **보수적으로 잡을수록** 일정이 다가올 때 조급함이 줄어든다.

| 등급 | 기준 | 앱에서의 예시 |
| --- | --- | --- |
| **P0** | 없으면 **빌드도 설치도 안 됨** | gradle 설정 · SDK 버전 · 팀 공용 디버그 서명 키 |
| **P1** | **메인 피처** — 없으면 프로젝트가 의미 없음 | 미니룸, 산책 게임 |
| P2 / P3 | 나머지 | 개발자 패널, 테마 추가, 문서 |

- CI/CD 는 P0 이 아니다. 없어도 동작한다. 이 저장소에는 아직 없다.

## 3. Iteration 과 작업량

Iteration 은 **3~4일**이다. **카드 하나 = PR 하나 = Iteration 하나.**

기간 전부를 구현에 쓸 수는 없다. 강의 기준으로 구현에 쓸 수 있는 시간은 기간의 절반이
못 된다. 나머지는 테스트 · 검증 · 리뷰에 들어간다.

| 기간 | 워킹데이 | 실제 구현 가능 |
| --- | --- | --- |
| 2주 | 10일 | 3~4일 (최대 5~6일) |
| 1주 | 5일 | 2일 |
| **3~4일 (이 프로젝트)** | 3~4일 | **1~2일** |

이 숫자를 그대로 AI 에게 준다.

```
Iteration 이 4일이고 구현에 쓸 수 있는 건 2일이야.
2일 안에 끝낼 수 있는 단위로 쪼개서 PR 작업 목록으로 올려줘.
```

앱에서는 여기에 **실기기 확인 시간**이 더 붙는다. 화면에서 봐야만 알 수 있는 것이 많고
(11절 사례: 눈이 3픽셀이면 어떻게 되는가 — [`HISTORY.md`](../HISTORY.md)), 한 번 보면
대개 다시 그려야 한다.

**폭포수 자가진단** — 계획이 한 줄로 쭉 내려와서 보기 편하면 폭포수다. 기획하면서
설계하고, 설계하면서 개발하는 **병행**이 있는지가 판별 기준이다.

## 4. PR 기준으로 일하기

**이슈는 쓰지 않는다.** 이슈는 사람이 관리하는 것이었고, AI 가 관리하려면 코드에 붙어
있어야 한다. GitHub 에서는 PR 도 이슈와 같은 번호 체계(`#1`)를 쓰므로, Project 는
`Open Pull Requests` 기준으로 관리한다. 이슈 템플릿도 두지 않는다. 누가 이슈를 열면
PR 이나 Project 의 draft 카드로 옮기고 닫는다.

**핵심 전환: PR 을 작업 "후"가 아니라 "전"에 연다.**

| | 기존 | 이 프로젝트 |
| --- | --- | --- |
| 시점 | 개발이 끝난 다음 | **할 일을 정리해서 먼저** |
| 내용 | 완료된 결과물 | **앞으로 할 일의 명세** |

### 순서

1. `dev` 에서 브랜치를 만들고 **draft PR 을 먼저 연다.** 제목이 곧 카드 이름이다
   (`타입: 무엇을`, 타입은 feat / fix / docs / refactor / build / chore).
   빈 브랜치로는 PR 이 안 열리니 빈 커밋 하나를 올린다.

   ```powershell
   git switch -c feat/breed-picker dev
   git commit --allow-empty -m "feat: 사용자용 견종 선택 화면"
   git push -u team feat/breed-picker
   gh pr create --draft --base dev      # 제목을 묻고, 본문은 템플릿이 뜬다
   ```

   ⚠️ **미리 열어 둔 카드에 착수할 때는 브랜치를 새로 파지 않는다.** 그 카드에는 이미
   브랜치가 있다. `git switch -c` 로 새 이름을 만들면 커밋이 전부 거기 쌓이고, PR 은
   **원래의 빈 브랜치를 그대로 머지**한다 — 에러가 하나도 안 나고 `dev` 에는 아무것도
   안 들어간다. 백엔드 저장소에서 2026-08-30 에 `#68` 이 그렇게 빈 채로 머지됐고, 작업
   8커밋이 다른 브랜치에 남았다. 착수 전에 **PR 이 쓰는 브랜치 이름부터 확인한다**:

   ```powershell
   gh pr view <번호> --json headRefName -q .headRefName
   git fetch team; git switch <그 이름>; git merge team/dev
   ```

2. Project 에 카드를 넣고 필드(담당자 / Priority / Size / Iteration)를 채운다.
   본문에는 필드가 담을 수 없는 것만 적는다 — 두 군데가 되면 반드시 어긋난다.
3. 작업 중 본문을 갱신한다. 특히 `## 컨텍스트 메모` 는 다음 세션의 Claude 가 읽는
   유일한 인수인계다.
4. 끝나면 draft 를 풀고 리뷰 → `dev` 머지.
5. 안 하게 됐으면 닫지 말고 Status 를 **Hold** 로 옮기고, 이유를 `## 컨텍스트 메모` 에
   한 줄 남긴다.

### 제목은 `타입:`, 커밋은 지금 방식 그대로

**PR 제목**은 `타입: 무엇을` 이다. 보드의 카드 이름이라 훑을 때 종류가 보여야 한다.

**커밋 메시지는 지금 방식을 유지한다.** 한글 서술형이고 `feat:` 같은 접두사를 붙이지
않는다. 무엇이 어떻게 잘못돼 있었는지를 제목에 쓰고(`~던 것`), 왜 그렇게 고쳤는지를
본문에 쓴다. 이 저장소의 커밋 60여 개가 전부 그렇게 쓰여 있다.

```
도감 2열에서 카드가 잘리던 것 - 칸이 행 높이로 늘어나던 탓
시바 세 색을 같은 그림으로 (저쪽 PR #17)
```

둘은 다른 것이다. **PR 제목 규칙을 커밋에 적용하지 않는다.**

### Project 필드

| 필드 | 기준 |
| --- | --- |
| Assignee | **카드를 열 때 작업자를 넣는다.** 비어 있으면 "아무도 안 잡은 것"과 "적기만 안 한 것"이 갈리지 않는다 |
| Priority | P0 ~ P3. **사람이 정한다.** 프로젝트 자체 필드다 — 조직 issue field 에서 파생된 Priority 는 이슈에만 값이 들어가서 PR · draft 카드에는 못 쓴다 |
| Size | 나를 위한 게 아니라 **남을 위한 것.** 구현이 그려지면 XS / S, 설계도 안 떠오르면 L / XL. **Claude 가 판단해 넣는다** — Priority 와 달리 사람 승인을 기다리지 않는다. 구현이 그려지는지는 코드를 본 쪽이 안다 |
| Iteration | 3~4일. 카드 하나가 하나의 Iteration 안에 끝나야 한다 |
| Status | 아래 흐름을 따른다 |

#### Status 흐름

```
Todo ──────→ In progress ──────→ Done
 카드를 열 때    착수할 때           머지되면 (Projects 가 옮긴다)
                     │
                     └──→ Hold   필요 없어졌거나 정의가 안 된 것
```

- **`Hold` 를 둔다.** 필요 없어진 것과 정의가 안 된 것을 구분해 두면 리뷰 때 백로그로
  되돌릴지 정할 수 있다. 닫지 말고 Hold 로 옮기고 이유를 `## 컨텍스트 메모` 에 한 줄 남긴다.
- **`In progress` 가 제일 잘 빠진다.** 규칙이 없어서가 아니라 **그 순간에 이 문서를 읽는
  사람이 없기 때문**이다 — 문서는 카드를 *열 때* 읽고, Status 를 바꿔야 하는 것은 며칠 뒤
  *착수할 때*라 시점이 어긋난다. 그래서 PR 템플릿의 `## 착수 절차` 첫 칸에 두어 눈앞에 오게 했다.
- **`Done` 은 손으로 옮기지 않는다.** PR 이 머지되면 Projects 가 옮긴다.
  ⚠ 다만 **Done 이 "작업이 `dev` 에 들어갔다"를 뜻하지는 않는다** — 백엔드 저장소에서
  2026-08-30 에 `#68` 이 빈 브랜치로 머지되면서 아무것도 안 들어갔는데도 Done 이 됐다.

- 다 같이 설계할 것은 **draft 카드**로 올린다. 프로젝트 참여자 전원이 볼 수 있다.
- `gh` 로 Project 를 읽고 쓰려면 `gh auth refresh -h github.com -s project` 를 한 번
  해 두어야 한다. 브라우저가 열리는 대화형이라 AI 가 대신 못 한다.

### 브랜치

- 작업 브랜치는 `dev` 에서 따고 PR 로 `dev` 에 머지한다. 머지된 브랜치는 자동
  삭제된다 (저장소 설정).
- `main` 은 릴리즈 스냅샷이다. 완성 단위마다 `dev → main` PR 로 올린다. `dev` 가
  default 라 이 머지로 `dev` 가 지워지지는 않는다 — **default 를 `main` 으로 바꾸지 말 것.**
- 개인 저장소에서 실험하는 것은 그대로 둔다. 실험은 개인 저장소에서, 정리되면 팀으로
  ([`HISTORY.md`](../HISTORY.md) 13절). 개인 실험 브랜치로는 PR 을 열지 않는다.

## 5. 데일리 스크럼

세 줄이면 된다. **15~30분, 짧게.** 뒤에 기다리는 사람이 있어야 끝난다.

1. 어제 뭐 했는지
2. 오늘 뭐 할 건지
3. **이슈가 뭐가 있는지**

PR 기준으로 확인한다: 어제 PR 에 커밋이 올라갔는지, **안 올라갔으면 왜** 안 올라갔는지.

AI 로 좋아진 건 **생산의 속도**지, 공유를 안 해도 된다는 게 아니다.

## 6. 회고 — 열기구

Iteration 이 끝날 때마다 한다. 한 사람당 포스트잇 **2장**이면 된다.

| 영역 | 무엇을 적나 |
| --- | --- |
| 🎈 **Hot air** | 잘된 점 |
| 🏋️ **Sandbag** | 아쉬운 점, 부족했던 점 |
| ☀️ Sunny day | (미래형일 때) 기대되는 것 |
| ⛈️ Storm cloud | (미래형일 때) 우려되는 것 |

1. 각자 붙이기 — **최대한 구체적으로**
2. 돌아가면서 왜 적었는지 설명
3. 이모지 · 스티커로 공감 투표
4. 공감 많이 받은 것 뽑기
5. 다음 Iteration 에 어떻게 반영할지 → **액션 카드.** Project 에 draft 카드로 올린다.
6. **다음 회고 때 액션 카드가 지켜졌는지 먼저 확인**

도구: [Miro](https://miro.com) (보드 3개까지 무료), [FunRetrospectives](https://funretrospectives.com)

회고는 프로덕트를 만드는 것과 유일하게 무관한 단계라 안 하게 된다. 그런데 Iteration
루프에는 쉬는 타이밍이 없어서, **회고가 유일한 쉼표**다.

## 7. 에셋과 실기기 — AI 에게 맡길 때

앱에는 인프라가 없다. 저쪽 문서의 7절(AWS / 자체 서버)은 해당 없다. 그런데 **같은
원칙이 그대로 걸리는 자리**가 둘 있다.

### 첫 프롬프트에 제약을 준다

그냥 만들라고 하면 AI 는 자기 기본값을 고른다. 앱에서는 그게 화풍 · 격자 · 리소스
형식으로 나온다. 실제로 겪은 것:

- 견종 25종의 크기를 **하나로 통일**해 버려서 치와와와 시베리안 허스키가 같은 크기로
  섰다. 저쪽 표에 견종마다 값이 따로 있는데 안 읽고 만든 결과다.
- PNG 를 `drawable-nodpi` 에 그대로 넣으면 57MB 다. WebP q92 를 거치면 7.5MB 다.

이미 정한 제약은 [`CLAUDE.md`](../CLAUDE.md) 와
[`docs/asset-workflow.md`](asset-workflow.md) 에 있다. **작업 시작 전에 이 둘을 먼저
읽힌다.**

### 설정은 AI 가 쓰되, 상태는 사람이 안다

코드는 AI 가 쓴다. 그런데 **지금 폰에 뭐가 깔려 있는지는 코드에 안 적혀 있다.**

- `adb` 인증이 수시로 풀린다. `adb install` 출력을 버리면 설치 실패를 못 보고
  **옛 APK 를 찍어놓고 새 그림이라고 보고하게 된다** (실제로 한 번 그랬다).
  그림을 바꿨으면 APK 를 되뽑아 해시로 대조한다 — 방법은 [`CLAUDE.md`](../CLAUDE.md).
- 저쪽 아트 저장소의 어느 브랜치가 최신인지도 코드에 없다. 받기 전에 사람이 확인한다.
- **폰은 사용자가 쓰는 물건이다.** 스크린샷을 찍기 전에 앱이 앞에 떠 있는지 확인한다.
