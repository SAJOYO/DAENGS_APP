# 완료 산책의 동선 구간과 장면 선택

완료 산책에서 `동선 탐색`을 열면 현재 경로의 각 연속 구간을 선택해 확대할 수 있다.
전체 보기는 멀리 떨어진 유효한 구간도 모두 포함한다. 구간 사이를 직선으로 연결하지 않는다.
기본 범위에서 먼 장면을 제외하는 처리는 기존 #311의 `diaryOverviewBounds`를 그대로 쓴다.

장면 선택, 구간 선택, 겹친 길의 통과 선택, 재생은 `WalkRouteSelection` 하나를 공유한다.
선택한 장면의 시점에 대응하는 방문만 강조하고, 기존 화면 좌표 기반 화살표 배치를 재사용한다.
대응하는 선이 없는 선택은 전체 동선 화살표로 되돌아가지 않는다. 장면 번호 핀은 그대로
보존하며 재생용 삼각형 커서는 장면 선택에 쓰지 않는다.

## 현재 읽기 모델의 범위

`CompletedRouteReview`는 `WalkSessionDetail`의 이미 계산된 경로를 읽는다. 새로운 GPS
정책이나 보행 판정기가 아니다. `CompletedRouteSection`의 index는 **이 화면에 로드된 경로
안에서만** 유효하며 장면에 저장하지 않는다. 각 구간은 기존 `WalkRouteSegment`다.
거리 합계와 기록 시간은 기존 summary를 유지한다. 표시 선의 기하 길이를 구간별 인정
보행거리처럼 보여주거나 합계에 다시 더하지 않는다.

DEV #467/#470의 불변 측정 계약과 그림자 계산은 공개 API·앱 캐시로 연결되지 않았다.
따라서 여기서 현재 세그먼트를 새 계약의 `ObservedRun`/`WalkingSection`으로 확정하지 않는다.
고속 제외와 GPS 공백을 분류할 근거가 없는 과거 기록에는 그 사유를 붙이지 않는다.

## 장면 대응 규칙

1. 같은 산책의 사건 시각이어야 한다. 위치 없는 장면은 본문을 열고 대응선·커서를 만들지 않는다.
2. 원본 관측 주소가 있는 자동 장면은 `clientSeq`, chain, 관측 시각과 원본 위치를 검증한다.
   현재 표시 경로에 그 관측점이 있어야 한다. 버려진 관측을 근처의 수용점이나 선분으로
   옮기지 않는다. 표시 경로가 관측을 생략한 경우에도 이번 단계에서는 대응 미확인으로 남긴다.
3. `WalkRoutePoint`는 제공된 단조 시각을 보존한다. 새 측정은 이 값까지 대조한다.
   legacy reader가 단조 시각을 버린 경우에는 기존 reader를 바꾸지 않고, 원본·경로의
   시각/좌표가 모두 유일할 때만 대응한다. 중복된 시각/좌표를 첫 번째 것으로 고르지 않는다.
4. 관측 주소 없는 사진·메모는 **발생 시각으로 먼저** 범위를 좁힌다. 정확히 하나의 기록점
   또는 기존 구간 안의 짧은 시간 범위가 있어야 하며 장면 위치도 12m 안에서 일치해야 한다.
   서로 다른 방문이 같은 벽시계 시각에 걸치면 좌표로 하나를 고르지 않고 미확인으로 남긴다.
5. 시간 보간은 기존 탐색기와 같이 활동·벽시계 간격이 각각 1–15초인 인접 점 사이에서만 한다.
   첫 위치 전, 마지막 위치 후, 긴 간격, 구간 경계를 건너뛰지 않는다. 이는 **화면 대응의 보수적
   기준**이고 보행거리 판정 기준이 아니다. 강조는 해당 위치 주변 최대 30초·약 40m로 제한하되,
   직접 이어진 인접 선분 하나는 길다는 이유만으로 없던 것으로 취급하지 않는다.
6. 서버 장면의 위치 판정 방법·위치 확인 시각·상태를 `DiarySceneContent`에 보존한다.
   마지막 확인 위치, 사건보다 이른 위치, provisional/legacy 위치를 현재 방문으로 주장하지 않는다.
   서버 content 없는 로컬 메모도 현재 entry의 위치 시각·pin 방법·상태를 확인한다.

표시용 `SceneRouteRelation`은 새 측정의 판정 원본이 아니다. 이번 장면 대응은 단일 사건
시점 기준이며 장면의 전체 지속 범위에 대한 다중 구간 binding은 후속 측정 연결에서 다룬다.

## 선택·갱신·경계

- `Overview / Section / Scene / Passage / Replay`는 배타적이다. 장면 ID만 구성 변경 시 보존한다.
  새 경로가 준비되면 일시적인 구간·통과 선택은 초기화하고 장면 ID의 대응은 현재 근거로 다시 계산한다.
- 통과 검색 응답은 index 동일성과 선택 revision이 모두 맞아야 반영한다. 장면/구간/재생으로
  바뀐 뒤 늦게 끝난 검색과 오류는 새 선택을 덮지 않는다.
- 장면의 대응은 현재 scene 값과 entry, 현재 detail로 만든 review에서 파생한다. 예전 detail의
  대응이나 재생점을 새 경로 위에 그리지 않는다. 별도의 비동기 binding 캐시는 만들지 않았다.
- 카메라는 선택과 별개인 사용자 요청이다. 구간 선택은 그 구간 범위를, 전체 보기는 전체
  경로를 명시적으로 요청한다. 시트를 닫는 동작은 다른 모드의 선택을 지우지 않는다.
  연결된 장면의 선택에는 최소 줌 18을 사용해 주변 방향을 읽을 공간을 확보하되 이미 더
  확대된 사용자 배율은 유지한다. 위치만 있는 장면에는 이 최소 배율을 강제하지 않는다.
- 지도 핀은 `동선 시작`/`동선 끝`, 가까우면 `동선 시작 · 끝`, 한 점이면 `확인 위치`다.
  `도착`이라는 이름으로 기록 종료를 추정하지 않는다. 동선 탐색에는 실제 기록 시작·종료
  시각과 각 표시 구간의 시작·끝 시각을 따로 보여준다.
- 장면이 준비 중이어도 경로 탐색과 재생은 사용할 수 있다.

## 검증

단위 테스트는 `CompletedRouteReviewTest`, `WalkRouteExplorerStateTest`,
`SessionRouteExplorerLayerStateTest`, `WalkCompletedRoutePresentationTest`,
`WalkDiaryMapScreenTest`와 기존 서버 장면 parser/경로/방향 배치/상세 진입 테스트를 선택한다.
원거리 재개, 왕복 방향, 관측 제외, 원본 식별 불일치, 중복 시각, legacy 시각 손실,
마지막 확인 위치, 장면 변경, 늦은 통과 검색, 구간 선택·화면 유지가 회귀 기준이다.

2026-09-12에 관련 12개 클래스 **80개 테스트 통과, 실패·오류·skip 0**을 확인했다.
`assembleDebug`도 통과했다. 전체 앱 테스트 실행 결과를 뜻하지 않는다.

폰에서는 별도 패키지 `com.daengs.app.routepreview`의 `WalkRouteReviewLabActivity`로 확인한다.
이 Activity는 로그인·API 설정이 없는 해당 패키지에서만 열리고 **메모리의 가상 기록만** 쓴다.
사용자 DB에 쓰거나 원본을 내보내지 않는다. production `WalkDiaryMapContent`, 탐색 상태,
대응 모델, 지도 레이어·NAVER SDK를 사용하되 DB/서버 reader까지 검증하는 화면은 아니다.

별도 패키지 빌드는 저장소 밖 Gradle init script의 `androidComponents.finalizeDsl`에서
debug `applicationIdSuffix = '.routepreview'`와 별도 Kakao scheme을 설정한다.
`-PslimAbi=arm64-v8a -PversionName=route-review-333`으로 빌드하고 `adb install -r`의
`Success`와 실행 패키지를 확인한다. 새 필터로 실제 기록 509m/951m를 재계산한 결과는 아니다.

SM-S931N에서 NAVER 지도 타일과 실제 오버레이로 두 원거리 구간의 전체 보기/개별 확대,
같은 벤치 왕복 장면의 반대 방향 화살표, 공백 메모·동선 끝 이후 사진의 무강조 상태를 확인했다.
정식 `com.daengs.app`은 1.1.2, 마지막 업데이트 2026-09-11 20:15:43으로 유지됐다.

## 후속 연결

서버의 확정 measurement와 원본 source range를 받을 때 이 임시 표시 구간/시간 대응을
그 결과의 읽기 모델로 교체한다. 길이·시간 slice, 다중 구간 장면 범위, 실제 기록 시간축의
공백 재생, 원본 509m/951m 비교와 기존 기록 전환은 그 이후 작업이다.
