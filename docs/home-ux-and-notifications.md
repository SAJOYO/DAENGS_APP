## 기준 기기

Pixel 3 XL(`crosshatch`), **411.4 × 845.7dp**.

⚠️ **`wm density` 를 믿지 말 것.** 이 기기는 `Physical density: 560 / Override density: 476`
을 보고하는데 **Compose 가 쓰는 값은 560** 이다. 476 으로 환산하면 동그라미가 67.9dp 로
나와 코드의 58dp 와 안 맞고, 560 으로 환산하면 58.0dp · 튀어나온 양 22.0dp 로 **코드와
정확히 맞는다.** 이 문서의 모든 dp 는 560 기준이다.

재는 방법은 둘을 섞었다. `uiautomator dump` 는 글자 노드의 자리를 주지만 **의미 없는
`Box` 는 안 내놓는다** — 그래서 흰 카드의 윗변·아랫변과 동그라미는 스크린샷에서 색
경계를 찾아 쟀다 (`DaengPink #E88D91` · `Surface #FFFFFF`). 카드 안에서 글자가 없는
세로줄(폭의 385dp 지점)을 써야 한다. 폭 200px 로 재면 「댕스 AI 챗봇」 글자를 밟아
경계가 여섯 개로 잡힌다.

**계산으로 때우지 말 것.** 시즌 행이 차지하는 띠를 `TextButton` 최소높이(40dp)로
계산해 25dp 라고 적었다가, 실제로 재니 **58dp** 였다. 글자는 17.4dp 뿐이다.

## 1. 하단 동그라미와 시즌 행

### 무엇이 문제였나

가운데 발바닥 동그라미(= 챗봇 진입점, `HomeScreen.kt:425` 의 `onCenter`)가 흰 바 위로
**지름의 38%** 나 나와 있어서, 바의 일부가 아니라 바 위에 얹힌 별개의 물체로 읽혔다.

그리고 시즌 행과 흰 바 사이가 **47.1dp** 비어 있었다. 출처가 둘이다.

```
시즌 행 글자 아래           694.6dp
  ↓ 25.1dp   내용 영역 안 — 시즌 행 띠의 남은 부분 + Spacer(4dp)
내용 영역 아래 끝           719.7dp   ← 동그라미 윗변도 여기
  ↓ 22.0dp   FabLift. 동그라미만 있고 나머지는 투명한 띠
하단바 흰 판 윗변           741.7dp
```

### 어떻게 정했나

| 손잡이 | 지금 | 새 값 | 자리 |
| --- | --- | --- | --- |
| `FabSize` | 58dp | **52dp** | `DaengsBottomBar.kt:71` |
| `FabLift` | 22dp | **6dp** | `DaengsBottomBar.kt:72` |
| 시즌 행 높이 | 58dp (실측) | **28dp 고정** | `HomeGameCard.kt` |
| 시즌 행 아래 `Spacer` | 4dp | **0dp** | `HomeScreen.kt:650` |

- **`FabLift` 한 숫자가 둘을 같이 푼다.** 튀어나온 양이 38%→12% 가 되고, 투명한 띠가
  16dp 줄어 시즌 행이 바에 붙고, 그 16dp 가 내용 영역으로 돌아와 방이 커진다.
- **`BarHeight 56dp` 와 흰 판의 윗변은 안 건드린다.** 50dp 로 줄이면 탭 라벨 아래가
  깎인다 (2026-09-18 실기기 확인, `DaengsBottomBar.kt:67` 경고).
- **52dp 아래로는 안 내려간다.** 48dp 가 손가락이 닿는 최소치다.
- `FabSize` 는 가로 레일(`DaengsNavRail`)도 함께 쓴다. 거기서는 튀어나오지 않으므로
  크기만 따라간다.

### 결과

시즌 행 글자에서 흰 바까지 **47.1dp → 약 11dp** (띠 28dp 안에서 글자 아래 5.3dp +
`FabLift` 6dp). 실기기에서 좁게 느껴지면 `Spacer` 를 4~6dp 로 되돌린다 — 숫자 하나다.

## 2. 챗봇 카드와 인벤토리 분리

### 재면서 버그를 하나 찾았다

**인벤토리 슬롯의 이름과 개수가 화면에 없다.** 잘린 것이 아니라 **배치조차 안 된다** —
`uiautomator` 계층에 그 글자 노드가 아예 없다.

```
카드 윗변            393.0dp
  패딩 10dp
탭 줄 (아이템·테마)   403.1 .. 425.4dp
  Spacer 6dp
슬롯 줄에 남은 높이    55.6dp      ← 슬롯이 필요한 건 88dp
카드 아랫변          497.0dp      (CardSlotHeight 104dp)
```

슬롯은 `패딩 7 + 썸네일 46 + 간격 2 + 이름 13 + 개수 13 + 패딩 7 = 88dp` 인데 **55.6dp
만 받는다.** 썸네일(53dp)까지 들어가고 이름·개수가 떨어져 나간다.
STATUS 「알려진 문제」에 없던 항목이다.

### 왜 한 칸을 같이 쓰고 있었나

`CardSlotHeight` 주석이 이유를 적어 뒀다 — *"둘의 높이가 다르면 방이 `weight(1f)` 로
남는 높이를 가져가기 때문에, 인벤토리를 열고 닫을 때마다 방 크기가 그 차이만큼 튄다"*
(`HomeScreen.kt:84`).

### 어떻게 정했나 — 분리하고, 튀는 것을 애니메이션으로 없앤다

**묶어 둔 이유가 「튄다」 하나였고, 3번이 그 튐을 없앤다.** 방 높이에
`animateDpAsState(tween(220))` 를 걸면 튀는 게 아니라 미끄러져서, *"인벤토리가 열리며
방이 조금 물러난다"* 는 납득되는 움직임이 된다. 묶어 둘 이유가 사라진다.

- 챗봇 카드 **104dp → 88dp**. 안에 든 것은 `패딩 7×2 + 제목줄 25 + Spacer 5 + 입력줄 44`.
  입력줄 46→44, 아바타 40→38 로 2dp 씩 줄인다 — 눈에 안 보이지만 방 16dp 는 보인다.
- 인벤토리는 **제 높이(약 140dp)** 를 쓴다. 이름과 개수가 돌아온다.
- **80dp 는 안 한다** — 입력줄이 40dp 로 내려가 손가락에 좁아진다.

### 거절한 안

- **슬롯을 납작하게 다시 만들어 계속 한 칸에 둔다** — 88dp 에 맞추려면 썸네일이 30dp
  대까지 내려간다. 픽셀 아트라 **무슨 아이템인지 알아볼 수 없게 된다.**
- **인벤토리를 방 위 시트로 옮긴다** — 이미 거절된 길이다. *"방 위에 겹치면 바닥을
  가려서 방금 놓은 물건이 안 보인다"* (`HomeScreen.kt:618`).

### 1·2 를 합친 결과

방 상자 **275.6dp → 335.3dp (+59.7dp, +22%).** 카드 블록이 통째로 내려가 바에 붙는다.

상자 높이는 `챗봇 카드 윗변(389.0dp) − 상단바 아랫변(113.4dp)` 이다. 상단바 아랫변은
로고 아래(107.4dp)에 패딩 6dp 를 더한 값이고, 그 위 상태바는 이 기기에서 48.9dp 다
(노치). **늘어나는 양 59.7dp 는 상단바와 무관**하므로 이 기준이 틀려도 증가분은 같다.

## 3. 화면 전환 모션

### 무엇이 문제였나

**내비게이션 라이브러리가 없다.** `MainActivity.kt:849` 의 `when (screen)` 하나가 화면
18개를 갈아 끼우고, 홈 안의 탭도 `HomeScreen.kt:528` 의 `if (tab == …) return@Scaffold`
로 갈린다. 전환 애니메이션이 들어갈 자리가 아예 없어서 "팍" 바뀐다.

그리고 **화면 15개가 지도·카메라 같은 `AndroidView` 를 안고 있다** (`ui/places` ·
`ui/walk` · `ui/game/owned` · `ui/gait` · `ui/camera`). 이것이 안을 고르는 데 결정적이다.

### 어떻게 정했나 — fade-through 한 겹

```
나가는 화면   90ms  alpha 1 → 0
들어오는 화면 210ms  alpha 0 → 1 · scale 0.92 → 1        합 300ms
```

- **300ms 는 이미 이 저장소의 값이다** — `IntroTimeline.VEIL_END_MS = 300L`, 로딩에서
  홈으로 넘어올 때 크림 막을 걷는 시간이다. 앱 전체가 한 박자로 움직인다.
- **레이아웃을 다시 재지 않는다.** `graphicsLayer` 의 alpha·scale 만 바뀌므로 지도
  15개 화면에 안전하다.
- **나가는 화면을 90ms 에 놓는다.** 슬라이드면 300ms 동안 지도 두 개가 동시에 살아
  있어야 한다 — Pixel 3 XL 에서 그럴 이유가 없다.
- **방향 개념이 필요 없다.** 그래서 화면 깊이 표도, 백스택도, **`BackHandler` 93곳
  손질도 없다.** 이 카드에 들어갈 크기가 되는 이유가 이것이다.

### 「로딩했다가 팍」 의 뒤쪽 절반

사용자가 말한 것은 두 가지가 겹친 것이다 — 전환이 컷인 것과, 그 앞에 로딩이 한 번
끼는 것. 뒤쪽은 이렇게 잡는다.

1. **로딩 → 내용도 fade 로** 잇는다. 지금은 이것도 컷이다.
2. **빨리 오는 로딩 표시는 아예 안 띄운다.** 이 판단도 이미 홈에 있다 —
   `DOGS_LOADING_DELAY_MS = 600L`, *"빠른 망에서는 목록이 눈 깜짝할 사이에 오는데,
   그때 표시가 떴다 사라지면 그것 자체가 깜빡임이다"* (`HomeScreen.kt:98`).
   **같은 상수를 다른 화면에도 쓴다.**
3. **방 높이 애니메이션** (2번이 요구하는 것) — `animateDpAsState`, 220ms.

### 거절한 안

- **방향 있는 슬라이드 (화면 깊이 표)** — 깊이 표를 화면 추가마다 손봐야 하고 빠뜨리면
  뒤로가기가 앞으로 가는 것처럼 보인다. 지도 화면에서 두 화면이 300ms 동안 동시에
  살아 있다. `BackHandler` 93곳의 목적지와 깊이 표가 어긋나면 방향이 거꾸로 난다.
  **A 를 실기기에서 보고 심심하면, 가벼운 화면에만 얹는 것은 나중에 싼 추가다.**
- **Navigation Compose 로 이주** — `MainActivity` 1830줄이 세션·강아지·산책 런타임을
  다 들고 있어서 route 로 쪼개면 전부 재배선이다. **별도 카드.**

## 4. 방 크기를 기기 사이에서 안정시킨다

### 무엇이 문제였나

`HomeScreen.kt:719` 의 세로 배치에서 방이 `weight(1f)` 로 **남는** 높이를 가져간다.
카드는 고정 높이라, **화면 높이 차이가 전부 방으로 간다.**

```
ROOM_PNG_W/H = 1122/1402 = 0.800      INSET = 0.94
방 보이는 폭 ≈ 0.75 × 상자 높이        (세로에 막혔을 때)
세로 대신 가로에 막히는 지점: 상자 높이 > 화면 폭 × 1.25 = 514dp
```

**어느 폰도 514dp 에 못 닿는다.** 그래서 방 크기가 상자 높이에 그대로 비례한다.
1·2 를 반영한 숫자다.

| | 화면 | 방 상자 | 방 보이는 폭 | 좌우 여백 |
| --- | --- | --- | --- | --- |
| Pixel 3 XL (실측) | 411×846 | **335dp** | 251dp | 80dp (39%) |
| Pixel 7 · S25 (계산) | 411×914 | **455dp** | 341dp | 35dp (17%) |
| 작은 폰 (계산) | 360×780 | 325dp | 244dp | 58dp (32%) |

상자 335 vs 455 — **36% 차이.**

Pixel 7 쪽 계산: `내용 영역 아래 끝 828 − 카드 블록 284.6 − 상단바 아랫변 88.5`.
3XL 보다 상단바가 낮고(상태바 24dp) 내비 인셋도 작다(제스처 24dp) — **그 차이까지
전부 방으로 간다.**

### 어떻게 정했나 — 방 그림에 최대 크기를 준다

상자는 지금처럼 `weight(1f)` 로 두고, `RoomGeometry.of` 안에서 **`contain` 에 상한을
씌운다** (`miniroom/IsoMath.kt:340`). 상자가 남으면 방 주위 공기가 된다.

- **레이아웃 분기를 안 건드린다.** wide · flex · scroll · 일반 네 갈래를 그대로 두고
  방 안쪽 계산만 바뀐다 — 위험이 제일 작다.
- `V_BIAS` 가 이미 있어 남는 공기를 위아래로 어떻게 나눌지 정할 수 있다.
- **순수 함수라 테스트가 된다.** 기기 크기 몇 개를 넣어 방이 상한을 안 넘는 것을 고정한다.

**상한 = 상자 높이 360dp 환산.** 여기엔 피할 수 없는 맞바꿈이 있다 — 작은 폰에
맞추면 통일되지만 큰 폰이 공간을 못 쓴다.

| 상한 | 큰 폰의 방 폭 | 3XL ↔ Pixel 7 차이 | 큰 폰이 버리는 세로 |
| --- | --- | --- | --- |
| 340dp | 255dp | 2% | 115dp |
| **360dp** | **270dp** | **8%** | **95dp** |
| 380dp | 285dp | 14% | 75dp |
| 없음 (지금) | 341dp | 36% | 0 |

3XL 은 335dp 라 **상한에 안 걸린다** — 방이 지금(1·2 반영 후)과 똑같다. 상한은 큰 폰을
작은 폰 쪽으로 끌어오는 장치다.

상수 하나로 빼 둔다 — 실기기에서 보고 조정할 자리다.

### 같이 손봐야 하는 것

`TodayCard` 와 `+` · `DEV` 는 **상자** 기준(`align(TopStart)` · `align(TopEnd)`)이라 큰
폰에서 방에서 떨어진다. 이름표는 이미 **방 그림** 기준으로 옮겨 놨으니
(`HomeScreen.kt:1015`) 같은 길로 옮긴다. 7번이 이 자리를 이미 건드린다.

### 거절한 안

- **상자 높이 자체에 `heightIn(max=…)`** — 상자가 줄면 `flexRoom`(힌지 선에 딱 맞춘
  값)과 `homeScrolls`(상자 높이로 갈래를 고른다)의 전제가 흔들린다.
- **방을 화면 폭에 맞추고 모자라면 홈을 스크롤로** — 상자를 `화면 폭 / 0.75 = 548dp`
  로 못 박으면 **모든 기기에서 방 폭이 같아진다.** 완전한 해결이고 시안에 가장 가깝다.
  그러나 **홈이 항상 스크롤 화면이 된다** (Pixel 7 에서 93dp, 3XL 에서 217dp 넘침).
  `"스크롤 없음 — 전부 한 화면에 들어간다"` 가 지금 설계 결정이고
  (`HomeScreen.kt:531`), **STATUS 「다음 결정」 5번이 이것을 기획 결정으로 파킹해 뒀다.**
  에이전트가 정할 자리가 아니다.

## 5. 저장소 탭을 요약 + 전체보기로 접는다

### 무엇이 문제였나

`ui/storage/ChatSummaryRoute.kt:134` 가 `LazyColumn` **하나**에 세 섹션을 세로로 이어
붙인다. 그런데 **세 섹션이 다 자라는 것은 아니다.**

| 섹션 | 자라나 | 지금 |
| --- | --- | --- |
| 오늘의 케어 기록 | 오늘 하루치라 상한이 있다 (그룹이면 식구 수만큼) | 전부 펼쳐 그린다 |
| 진료비 | **안 자란다** | 이번 달 합계 · 마지막 방문 · 「전체보기 ›」 → `VetVisitsScreen` |
| 대화 보관함 | **무한히 자란다** | 요약을 전부 항목으로 펼친다 |

**진료비가 이미 답을 보여 줬다.** 요약으로 접고 자세한 건 전용 화면이 받는다. 그래서
기록이 쌓여도 저장소 탭이 안 길어진다. **대화 보관함만 그 규칙 밖에 있고, 하필 목록
맨 끝이라** 스크롤 전체를 끌고 늘어난다.

덤으로, 지금은 요약을 보려면 항상 케어·진료비를 지나쳐야 해서
`animateScrollToItem(index + HEADER_ITEMS)` 같은 코드가 있다 (`:122`, `HEADER_ITEMS = 3`).
**머리 항목 수를 손으로 세어 맞추는 코드**라 섹션을 하나 넣을 때마다 밟을 자리다.

### 어떻게 정했나 — 진료비 패턴을 세 섹션에 다 적용

```
오늘의 케어 기록    오늘 챙긴 것 요약        → 전체보기 (날짜별)   ← 새 화면
진료비             이번 달 · 마지막 방문     → 전체보기            ← 이미 있음
대화 보관함        최근 2~3건               → 전체보기            ← 새 화면
사진               준비 중
```

- **탭 높이가 내용과 무관하게 고정된다.** 기록이 천 건이어도 저장소 탭은 그대로다.
- **이 저장소가 이미 고른 답**을 따르므로 새 개념을 안 만든다. `VetVisitsScreen` 이
  본보기라 형태도 이미 있다.
- `HEADER_ITEMS` 와 손으로 세는 스크롤 계산이 **사라진다** — 선택된 요약으로 가는
  동작은 전체보기 화면으로 옮겨가고, 거기선 목록이 하나뿐이라 셀 게 없다.

⚠️ **저장소 탭의 지금 높이는 재지 않았다.** 실제 케어·진료비 기록이 화면에 뜨는
자리라 사용자 허락 없이 열지 않았다. "스크롤이 얼마나 줄어드나" 는 **구현 때 실기기에서
확인한다.**

### 거절한 안

- **저장소 안에 하위 탭 셋** — 도감이 이미 탭 셋(야채·과일·포토)이라 같은 장치가 앱에
  두 벌 생긴다. 그리고 **저장소를 열면 무엇을 보러 왔는지 먼저 골라야 한다** — 지금은
  열면 한눈에 다 보이는데 그 성질을 잃는다.
- **섹션 접기(아코디언)** — 접힌 상태를 기억해야 하고, 기본값을 무엇으로 두든 누군가는
  매번 펼친다. 사용자에게 정리를 떠넘기는 방식이다.

## 6. 알림

### 지금 있는 것

사용자를 부르는 알림이 **하나** 있다 — 보행 분석 완료 (`gait/work/GaitAnalysisWork.kt:155`).
그리고 그것이 잘 만들어져 있어서 **본보기가 이미 저장소 안에 있다.**

```
채널 분리      "한 채널에 묶으면 사용자가 둘 중 하나만 끄지 못한다"  (walk_tracking ≠ gait_analysis)
권한 확인      areNotificationsEnabled()
SINGLE_TOP    "CLEAR_TOP 을 주면 보던 화면이 홈으로 초기화된다" — 앱을 앞으로만 데려온다
어디로 갈지    putExtra(EXTRA_OPEN_GAIT_RECORD, …)
중복 방지      notify(id = recordId.hashCode()) — 다시 돌아도 같은 자리에 덮어쓴다
색            setColor(BrandPrimary)   ⛔ docs/design-locks.md 0절
```

`POST_NOTIFICATIONS` 권한은 이미 선언돼 있고(`AndroidManifest.xml:28`) 두 곳에서
요청한다 (`ui/walk/WalkRoute.kt:172` · `ui/chat/ChatScreen.kt:640`).

### 무엇을 알리나 — 사용자가 고른 다섯

| # | 알림 | 어디에 붙나 |
| --- | --- | --- |
| 5 | 보행 분석이 끝났어요 | `GaitAnalysisWork` — **이미 있음** |
| 6 | 산책 기록을 못 보냈어요 | `WalkDeliveryWorker` 의 `Result.failure()` (`walk/sync/WalkDelivery.kt:107`) |
| 8 | 산책 일기 장면이 준비됐어요 | 같은 Worker 의 `Result.success()` — `syncPendingSession` 이 분석까지 왕복한다 |
| 13 | ○○의 생일이에요 | 새 일일 Worker + 강아지 정보 |
| 14 | ○○가 가족이 된 날이에요 | 13번과 같은 Worker |

사용자는 **리마인더를 뺐다** (카드 충전 · 저녁 산책). 앱이 조르지 않는 쪽이다.

### 채널 셋

성격이 다르면 나눈다 — `GaitAnalysisWork.ensureChannel` 주석의 그 규칙이다.

| 채널 id | 이름 | 중요도 | 알림 |
| --- | --- | --- | --- |
| `analysis_result` | 분석 결과 | DEFAULT | 5 · 8 |
| `sync_problem` | 보내지 못한 기록 | DEFAULT | 6 — 사용자가 손을 써야 하는 것 |
| `anniversary` | 기념일 | DEFAULT | 13 · 14 |

**`gait_analysis` 채널 id 를 `analysis_result` 로 바꾼다.** 8번이 같은 채널에 들어오면
`gait_` 라는 이름이 하는 일과 어긋나는데, 이 저장소는 그걸 안 둔다 (`BottomTab.Storage`
주석: *"이름표와 하는 일이 어긋난 채로 두지 않는다"*). **아직 출시 전이라** 옛 채널을
지워도 잃을 사용자 설정이 없다.

### 기념일 Worker

- 일일 반복 하나가 강아지 목록을 보고 **오늘이 그날인지만** 본다. 아침 9시.
- **생일을 안 넣은 강아지는 건너뛴다.** 온보딩에서 이름 말고는 전부 비워 둘 수 있게
  해 놨으니, 없는 값을 지어내지 않는다.
- ⚠️ **정확한 시각은 보장되지 않는다.** `AlarmManager.setExactAndAllowWhileIdle` 은
  Android 12+ 에서 `SCHEDULE_EXACT_ALARM` 권한이고 **Play 정책이 용도를 제한한다** —
  알람·캘린더 앱이 아니면 거절될 수 있다. `WorkManager` 로 가고 **±30분 늦을 수 있는
  것을 받아들인다.** 기념일 알림에 분 단위 정확도는 필요 없다.

### 종 아이콘 = 알림 설정

지금 `onBell = {}` 라 **눌러도 아무 일이 없는 버튼**이 상단바에 있다
(`HomeScreen.kt:453`). 여기에 설정 화면을 붙인다.

```
알림
  분석이 끝났을 때          [켬]
  기록을 보내지 못했을 때    [켬]
  기념일                   [켬]

  안드로이드 알림 설정 열기 ›
```

- **스위치를 켤 때 권한을 묻는다.** 알림을 켜겠다고 누르는 순간이 가장 정직한 타이밍이다.
- 권한이 거부돼 있으면 **그 사실을 말하고** 안드로이드 설정으로 보낸다 — 스위치만
  켜지고 알림이 안 오는 상태를 만들지 않는다.
- 저장은 SharedPreferences.

### 공용 헬퍼

`GaitAnalysisWork.notify()` 의 패턴을 `notify/DaengsNotifications.kt` 로 빼고 다섯이
그것을 쓴다. **후속 알림이 각 3~5줄이 되는 것이 이 작업의 목적이다.**

### 안 넣은 것

- **9. 피부 진단 결과** — 사용자가 뺐다. 진단이 `ui/chat/AssistantChat.kt` ·
  `ChatScreen.kt` 의 **화면 스코프**에 있어서, 알림을 붙이려면 먼저 Worker 로 옮겨야
  한다. 보행 분석은 이미 옮겨져 있는데(`GaitAnalysisWork` + `GaitPendingWatches` +
  `GaitWatch`) 피부 진단은 안 옮겨졌다 — **같은 성질의 일인데 처리가 갈려 있고, 지금은
  진단 중에 화면을 나가면 결과를 잃을 수 있다.** 별도 카드가 필요하다.
- **푸시(FCM)** — 탈취 알림 · 식구의 기록 · 그룹 초대. `DAENGS_dev` 에 FCM 키 · 토큰
  등록 API · 발송 로직이 먼저 있어야 한다. **저쪽 저장소 작업이 선행 조건이다.**
- **알림함** (기기에 쌓인 알림 목록) — Room 테이블 + 목록 + 읽음 상태 + 배지라 별도
  카드 크기다. 그리고 **그 값은 푸시가 생긴 뒤에 커진다** — 로컬 알림 다섯뿐이면
  안드로이드 알림 그림자로 충분하다.
- **배웅한 아이를 기억하는 날** — 이 앱은 배웅을 삭제와 다르게 편지와 하트로 아주
  조심스럽게 다룬다 (`HISTORY` · PR #76~#80). 알림이 그 결을 깨뜨릴 수 있고 **예고
  없이 오면 상처가 된다.** 넣더라도 기본 꺼짐 + 사용자가 직접 켜는 것이어야 하고,
  그건 사용자와 한 번 더 이야기할 자리다.

## 7. `+` 편집에서 날짜·이름표 자리를 고른다

### 자유 드래그를 안 하는 이유

이름표 규격이 이미 답을 적어 뒀다 — *"가로는 방 그림의 정중앙이라 상수가 없다.
`BottomCenter` 로 맞추면 글자가 길어져도 가운데가 유지된다. **백분율로 잡으면 이름이
길어질 때 한쪽으로 밀린다**"* (`HomeScreen.kt:112`).

자유 드래그로 가로 좌표를 %로 저장하면 **이 저장소가 이미 거절한 버그를 다시 만든다.**
더해서 `TodayCard` 는 접었다 펴면 높이가 변하고(아래쪽에 두면 펼칠 때 방을 덮는다),
방 크기가 기기마다 달라 작은 폰에서 두 카드가 겹친다.

### 어떻게 정했나 — 자리 고르기

```
  위왼쪽 ──── 위가운데 ──── [ +  DEV ]      위오른쪽은 제외 (버튼 자리)
    │                          │
    │        (방  그  림)       │
    │                          │
  아래왼쪽 ── 아래가운데 ── 아래오른쪽
```

**자리 다섯.** 위오른쪽은 `+`(46dp)와 `DEV` 가 쓰는 자리라 뺀다
(`align(TopEnd).padding(end=14, top=14)`).

- 각 자리는 **(가로 정렬, 세로 %)** 다 — 가로를 `Alignment` 로 두니 이름이 길어져도
  안 밀리고, `TodayCard` 를 접었다 펴도 안 흔들린다. `NamePlateSpec` 이 고른 방식 그대로다.
- **기준은 상자가 아니라 방 그림.** 상자 기준이면 방이 상자보다 작아질 때 카드가 방 밖
  배경 위에 뜬다 — 이름표가 이미 그랬다 (`HomeScreen.kt:1017`, 에뮬 실측 64%).
- **이미 찬 자리에 놓으면 둘이 자리를 바꾼다 (swap).** 잠그면 "왜 여기엔 못 놓지" 하는
  막힌 자리가 생긴다. swap 이면 잠금도 겹침 판정도 막힌 자리도 없다.
- **기본값은 지금 그대로** — 날짜=위왼쪽, 이름표=아래가운데. 아무것도 안 만지면 화면이
  지금과 똑같다.
- 저장은 `RoomStore` 에 키 둘. `RoomCodec` 은 소품 격자용이라 **안 건드린다.**
- 편집 중 **「기본 자리로」** 한 줄을 둔다.
- **위가운데는 창문을 가린다.** 창밖은 실제 시각·날씨를 따라 여섯 벌이 바뀌고 TODAY
  카드의 날씨와 같은 값이다. 그래도 자리로 열어 두기로 **사용자가 정했다** — "내 방이니
  내가 정한다" 쪽이다.

## 검증

**모션과 그림은 테스트로 못 잡는다** (`CLAUDE.md`: *"테스트는 좌표·배치·규격을 잡는다.
그림이 예쁜지는 못 잡는다"*). 그래서 이렇게 가른다.

### 테스트가 잡는 것

| 무엇 | 어떻게 |
| --- | --- |
| 하단바 규격 | 새 `HomeBottomBarLockTest` — `FabSize` · `FabLift` · `BarHeight` · 시즌 행 높이 |
| 방 크기 상한 | 기기 크기 여러 개를 `RoomGeometry.of` 에 넣어 상한을 안 넘는 것 |
| 카드 자리 | 자리 5개 × 기기 크기 몇 개로 **카드가 방 그림 밖으로 안 나가는 것** |
| 전환 스펙 | 순수 함수 — 총 300ms, 나가는 쪽이 들어오는 쪽보다 먼저 끝남 |
| 인벤토리 슬롯 | 슬롯이 필요한 높이를 받는 것 (지금 깨진 그 자리) |
| 기념일 판정 | 생일이 빈 강아지를 건너뛰는 것, 오늘 판정 |
| 저장소 요약 | 섹션이 요약만 그리고 목록 길이와 무관하게 높이가 고정인 것 |

### 실기기가 잡는 것

- 1·2 의 최종 숫자 — 시즌 행이 바에 붙은 느낌, 동그라미 크기
- 4 의 상한 360dp — 큰 폰에서 공기가 어색하지 않은지
- 3 의 모션 — `adb shell screenrecord` 로 녹화해 프레임 시트로 본다
- 5 의 스크롤 감소량 — 실제 기록이 있는 계정에서
- 6 의 알림 — 실제로 뜨는지, 눌렀을 때 보던 화면이 안 날아가는지

⚠️ `adb install` 출력에 `Success` 가 뜨는지 **직접 본다** (`CLAUDE.md`).

## 열린 질문

- **시즌 행 ↔ 흰 바 11dp** 가 좁으면 `Spacer` 를 4~6dp 로 되돌린다. 실기기 확인 후.
- **방 상한 360dp** — 큰 폰에서 봐야 안다. 상수 하나.
- **7번 자리 목록에 위왼쪽이 들어가는지** — 사용자가 "위가운데 · 아래왼쪽 · 아래가운데 ·
  아래오른쪽만 해도 돼" 라고 했다. 위왼쪽은 날짜의 기본 자리라 빼면 기본 배치가 바뀌므로
  **포함으로 읽었다.** 아니면 넷으로 줄인다.
