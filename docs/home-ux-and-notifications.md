## 기준 기기

Pixel 3 XL(`crosshatch`), **411.4 × 845.7dp**.

⚠️ **`wm density` 를 믿지 말 것 — 이 앱은 자를 직접 바꾼다.**

`DaengsTheme` 이 `LocalDensity` 를 갈아끼운다 (`ui/theme/Theme.kt:115`).

```kotlin
LocalDensity provides Density(base.density * scale, fontScale = 1f)
scale = uiScale(짧은 변) = (짧은 변 dp / 411).coerceIn(0.85, 1.25)
```

**그래서 합성 안에서 화면 폭은 어느 폰에서나 411dp 다.** 이 기기는 시스템이 484dp 로
보는데 `scale = 484/411 = 1.178` 이 걸려 합성 밀도가 `2.975 × 1.178 = 3.504` 가 된다.
`1dp = 3.504px` 이고, 그 자로 재면 동그라미가 **58.0dp · 튀어나온 양 22.0dp** 로 코드와
정확히 맞는다. `wm density` 의 476 으로 환산하면 67.9dp 가 나와 안 맞는다.

**합성 세로는 비율이 정한다** — `411 × (물리 세로 / 물리 가로)`. 이 문서의 모든 dp 는
이 자(3.504px/dp) 기준이고, **코드의 dp 리터럴과 같은 단위**다.

재는 방법은 둘을 섞었다. `uiautomator dump` 는 글자 노드의 자리를 주지만 **의미 없는
`Box` 는 안 내놓는다** — 그래서 흰 카드의 윗변·아랫변과 동그라미는 스크린샷에서 색
경계를 찾아 쟀다 (`DaengPink #E88D91` · `Surface #FFFFFF`). 카드 안에서 글자가 없는
세로줄(폭의 385dp 지점)을 써야 한다. 폭 200px 로 재면 「댕스 AI 챗봇」 글자를 밟아
경계가 여섯 개로 잡힌다.

**계산으로 때우지 말 것.** 시즌 행이 차지하는 띠를 `TextButton` 최소높이(40dp)로
계산해 25dp 라고 적었다가, 실제로 재니 **58dp** 였다. 글자는 17.4dp 뿐이다.

## 1. 하단 동그라미와 시즌 행

### 무엇이 문제였나

가운데 발바닥 동그라미(= 챗봇 진입점, `HomeScreen.kt:425` 의 `onCenter`)가 흰 바 위로
**지름의 38%** 나 나와 있어서, 바의 일부가 아니라 바 위에 얹힌 별개의 물체로 읽혔다.

그리고 시즌 행과 흰 바 사이가 **47.1dp** 비어 있었다. 출처가 둘이다.

```
시즌 행 글자 아래           694.6dp
  ↓ 25.1dp   내용 영역 안 — 시즌 행 띠의 남은 부분 + Spacer(4dp)
내용 영역 아래 끝           719.7dp   ← 동그라미 윗변도 여기
  ↓ 22.0dp   FabLift. 동그라미만 있고 나머지는 투명한 띠
하단바 흰 판 윗변           741.7dp
```

### 어떻게 정했나

| 손잡이 | 지금 | 새 값 | 자리 |
| --- | --- | --- | --- |
| `FabSize` | 58dp | **52dp** | `DaengsBottomBar.kt:71` |
| `FabLift` | 22dp | **6dp** | `DaengsBottomBar.kt:72` |
| 시즌 행 높이 | 58dp (실측) | **28dp 고정** | `HomeGameCard.kt` |
| 시즌 행 아래 `Spacer` | 4dp | **0dp** | `HomeScreen.kt:650` |

- **`FabLift` 한 숫자가 둘을 같이 푼다.** 튀어나온 양이 38%→12% 가 되고, 투명한 띠가
  16dp 줄어 시즌 행이 바에 붙고, 그 16dp 가 내용 영역으로 돌아와 방이 커진다.
- **`BarHeight 56dp` 와 흰 판의 윗변은 안 건드린다.** 50dp 로 줄이면 탭 라벨 아래가
  깎인다 (2026-09-18 실기기 확인, `DaengsBottomBar.kt:67` 경고).
- **52dp 아래로는 안 내려간다.** 48dp 가 손가락이 닿는 최소치다.
- `FabSize` 는 가로 레일(`DaengsNavRail`)도 함께 쓴다. 거기서는 튀어나오지 않으므로
  크기만 따라간다.

### 결과

시즌 행 글자에서 흰 바까지 **47.1dp → 약 11dp** (띠 28dp 안에서 글자 아래 5.3dp +
`FabLift` 6dp). 실기기에서 좁게 느껴지면 `Spacer` 를 4~6dp 로 되돌린다 — 숫자 하나다.

## 2. 챗봇 카드와 인벤토리 분리

### 재면서 버그를 하나 찾았다

**인벤토리 슬롯의 이름과 개수가 화면에 없다.** 잘린 것이 아니라 **배치조차 안 된다** —
`uiautomator` 계층에 그 글자 노드가 아예 없다.

```
카드 윗변            393.0dp
  패딩 10dp
탭 줄 (아이템·테마)   403.1 .. 425.4dp
  Spacer 6dp
슬롯 줄에 남은 높이    55.6dp      ← 슬롯이 필요한 건 88dp
카드 아랫변          497.0dp      (CardSlotHeight 104dp)
```

슬롯은 `패딩 7 + 썸네일 46 + 간격 2 + 이름 13 + 개수 13 + 패딩 7 = 88dp` 인데 **55.6dp
만 받는다.** 썸네일(53dp)까지 들어가고 이름·개수가 떨어져 나간다.
STATUS 「알려진 문제」에 없던 항목이다.

### 왜 한 칸을 같이 쓰고 있었나

`CardSlotHeight` 주석이 이유를 적어 뒀다 — *"둘의 높이가 다르면 방이 `weight(1f)` 로
남는 높이를 가져가기 때문에, 인벤토리를 열고 닫을 때마다 방 크기가 그 차이만큼 튄다"*
(`HomeScreen.kt:84`).

### 어떻게 정했나 — 분리하고, 튀는 것을 애니메이션으로 없앤다

**묶어 둔 이유가 「튄다」 하나였고, 3번이 그 튐을 없앤다.** 방 높이에
`animateDpAsState(tween(220))` 를 걸면 튀는 게 아니라 미끄러져서, *"인벤토리가 열리며
방이 조금 물러난다"* 는 납득되는 움직임이 된다. 묶어 둘 이유가 사라진다.

- 챗봇 카드 **104dp → 88dp**. 안에 든 것은 `패딩 7×2 + 제목줄 25 + Spacer 5 + 입력줄 44`.
  입력줄 46→44, 아바타 40→38 로 2dp 씩 줄인다 — 눈에 안 보이지만 방 16dp 는 보인다.
- 인벤토리는 **제 높이(약 140dp)** 를 쓴다. 이름과 개수가 돌아온다.
- **80dp 는 안 한다** — 입력줄이 40dp 로 내려가 손가락에 좁아진다.

### 거절한 안

- **슬롯을 납작하게 다시 만들어 계속 한 칸에 둔다** — 88dp 에 맞추려면 썸네일이 30dp
  대까지 내려간다. 픽셀 아트라 **무슨 아이템인지 알아볼 수 없게 된다.**
- **인벤토리를 방 위 시트로 옮긴다** — 이미 거절된 길이다. *"방 위에 겹치면 바닥을
  가려서 방금 놓은 물건이 안 보인다"* (`HomeScreen.kt:618`).

### 1·2 를 합친 결과

방 상자 **275.6dp → 335.3dp (+59.7dp, +22%).** 카드 블록이 통째로 내려가 바에 붙는다.

상자 높이는 `챗봇 카드 윗변(389.0dp) − 상단바 아랫변(113.4dp)` 이다. 상단바 아랫변은
로고 아래(107.4dp)에 패딩 6dp 를 더한 값이고, 그 위 상태바는 이 기기에서 48.9dp 다
(노치). **늘어나는 양 59.7dp 는 상단바와 무관**하므로 이 기준이 틀려도 증가분은 같다.

## 3. 화면 전환 모션

### 무엇이 문제였나

**내비게이션 라이브러리가 없다.** `MainActivity.kt:849` 의 `when (screen)` 하나가 화면
18개를 갈아 끼우고, 홈 안의 탭도 `HomeScreen.kt:528` 의 `if (tab == …) return@Scaffold`
로 갈린다. 전환 애니메이션이 들어갈 자리가 아예 없어서 "팍" 바뀐다.

그리고 **화면 15개가 지도·카메라 같은 `AndroidView` 를 안고 있다** (`ui/places` ·
`ui/walk` · `ui/game/owned` · `ui/gait` · `ui/camera`). 이것이 안을 고르는 데 결정적이다.

### 어떻게 정했나 — fade-through 한 겹

```
나가는 화면   90ms  alpha 1 → 0
들어오는 화면 210ms  alpha 0 → 1 · scale 0.92 → 1        합 300ms
```

- **300ms 는 이미 이 저장소의 값이다** — `IntroTimeline.VEIL_END_MS = 300L`, 로딩에서
  홈으로 넘어올 때 크림 막을 걷는 시간이다. 앱 전체가 한 박자로 움직인다.
- **레이아웃을 다시 재지 않는다.** `graphicsLayer` 의 alpha·scale 만 바뀌므로 지도
  15개 화면에 안전하다.
- **나가는 화면을 90ms 에 놓는다.** 슬라이드면 300ms 동안 지도 두 개가 동시에 살아
  있어야 한다 — Pixel 3 XL 에서 그럴 이유가 없다.
- **방향 개념이 필요 없다.** 그래서 화면 깊이 표도, 백스택도, **`BackHandler` 93곳
  손질도 없다.** 이 카드에 들어갈 크기가 되는 이유가 이것이다.

### 「로딩했다가 팍」 의 뒤쪽 절반

사용자가 말한 것은 두 가지가 겹친 것이다 — 전환이 컷인 것과, 그 앞에 로딩이 한 번
끼는 것. 뒤쪽은 이렇게 잡는다.

1. **로딩 → 내용도 fade 로** 잇는다. 지금은 이것도 컷이다.
2. **빨리 오는 로딩 표시는 아예 안 띄운다.** 이 판단도 이미 홈에 있다 —
   `DOGS_LOADING_DELAY_MS = 600L`, *"빠른 망에서는 목록이 눈 깜짝할 사이에 오는데,
   그때 표시가 떴다 사라지면 그것 자체가 깜빡임이다"* (`HomeScreen.kt:98`).
   **같은 상수를 다른 화면에도 쓴다.**
3. **방 높이 애니메이션** (2번이 요구하는 것) — `animateDpAsState`, 220ms.

### 거절한 안

- **방향 있는 슬라이드 (화면 깊이 표)** — 깊이 표를 화면 추가마다 손봐야 하고 빠뜨리면
  뒤로가기가 앞으로 가는 것처럼 보인다. 지도 화면에서 두 화면이 300ms 동안 동시에
  살아 있다. `BackHandler` 93곳의 목적지와 깊이 표가 어긋나면 방향이 거꾸로 난다.
  **A 를 실기기에서 보고 심심하면, 가벼운 화면에만 얹는 것은 나중에 싼 추가다.**
- **Navigation Compose 로 이주** — `MainActivity` 1830줄이 세션·강아지·산책 런타임을
  다 들고 있어서 route 로 쪼개면 전부 재배선이다. **별도 카드.**

## 4. 각 폰에서 방을 최대한 크게

> ⚠️ **이 절은 한 번 다시 썼다.** 처음에는 "기종마다 다르다" 를 **통일** 문제로 읽고
> 방 크기에 상한(천장)을 두자고 했다. 사용자가 원한 것은 통일이 아니라
> **"각 폰에서 방이 최대한 크게"** 였다. 상한은 잘 나오는 폰을 끌어내려 평평하게
> 만드는 장치라 정반대였다 — 버렸다.

### 무엇이 문제였나

`HomeScreen.kt:719` 의 세로 배치에서 방이 `weight(1f)` 로 **남는** 높이를 가져간다.
카드는 고정 높이라, **화면 세로 차이가 전부 방으로 간다.** 그리고 합성 폭은 어느 폰이나
411dp 이므로(위 「기준 기기」), 세로는 **화면 비율**이 정한다.

```
ROOM_PNG_W/H = 1122/1402 = 0.800      INSET = 0.94
방 그림 폭 = 1122 × sx
  sx = min(s × H_STRETCH,  상자폭 × 0.94 / 1122)     ← 상자 폭에서 잘린다
  s  = min(상자폭/1122, 상자높이/1402) × 0.94
방 그림 폭의 한계 = 411.4 × 0.94 = 386.7dp            ← 모든 폰에서 같다
```

1·2 를 반영한 숫자다.

| 폰 | 비율 | 합성 세로 | 방 상자 | 지금(1.18) 방 그림 폭 | 한계까지 필요한 `H_STRETCH` |
| --- | --- | --- | --- | --- | --- |
| **Pixel 3 XL (기준 기기)** | 2.06 | 846dp | **335dp** | **297.7dp** (한계의 77%) | **1.53** |
| Galaxy S25 | 2.17 | 890dp | 429dp | 380.9dp (98%) | 1.20 |
| Pixel 7 | 2.22 | 913dp | 452dp | **386.7dp — 이미 한계** | 1.14 |
| 21:9 | 2.33 | 959dp | 498dp | **386.7dp — 이미 한계** | 1.03 |

**길쭉한 폰은 이미 방이 화면 폭을 꽉 채운다.** 모자란 것은 정사각에 가까운 폰뿐이고,
기준 기기가 그중 최악의 경우다 — 89dp 부족하다.

### 어떻게 정했나 — 가로 늘림을 실기기에서 고른다

손잡이는 `RoomSpec.H_STRETCH` 다 (`miniroom/IsoMath.kt:93`, 지금 1.18). 방을 **가로로만**
늘리고, 상자 폭에서 자동으로 잘린다. 올리면 정사각에 가까운 폰이 한계까지 따라오고,
**길쭉한 폰은 이미 한계라 아무 변화가 없다.**

- `H_STRETCH` 를 **개발자 패널의 슬라이더**로 뺀다 (1.0 ~ 1.6, 디버그 전용·세션 한정).
- 사용자가 실기기에서 돌려 보고 값을 고른다. **기준 기기가 최악의 경우라 판단에 가장
  좋은 조건이다.**
- 고른 값을 상수로 굳히고 `docs/design-locks.md` 에 잠근다.
- **기본값은 1.18 그대로 둔다** — 고르기 전까지 화면이 안 변한다.
- **상한(천장)은 두지 않는다.** 통일이 목적이 아니다.

### 늘림의 실제 대가 — 러그가 아니라 모양이다

⚠️ **`H_STRETCH` 의 주석이 낡아서 대가를 잘못 말하고 있다.**

> *"강아지와 소품은 안 늘어난다… 대신 격자가 같이 늘어나므로 여러 칸을 차지하는
> 소품(러그 5x5)은 자기 칸을 다 덮지 못한다 — 늘릴수록 그 어긋남이 커진다"*
> (`IsoMath.kt:86`)

**그 문제는 이미 해결됐다.** 나중에 추가된 `RoomGeometry.scaleX` 가 소품에만 가로
배율을 준다 (`IsoMath.kt:184`).

| 무엇 | 배율 | 자리 |
| --- | --- | --- |
| 소품 | `scale(g.scaleX, g.scale)` — **가로만 같이 늘린다** → 칸을 덮는다 | `MiniRoomDrawing.kt:42` |
| 강아지 | `g.scale * dog.sizeScale` — **안 늘린다** → 개가 뚱뚱해지지 않는다 | `MiniRoomDrawing.kt:161` |
| 터치 판정 | `scaleX` 를 쓴다 — 그린 모양과 누르는 자리가 일치 | `MiniRoomState.kt:25`·`48` |

두 주석이 서로 모순하고, **낡은 쪽을 읽으면 "늘리면 러그가 깨진다" 는 틀린 근거로
판단하게 된다.** 실제로 이 작업에서 그럴 뻔했다. 주석을 고치는 것을 과제에 넣는다.

늘림의 진짜 대가는 이렇다 — **전부 "예쁜지" 라서 테스트로 못 잡고 실기기에서 봐야 한다.**

| 대가 | 설명 |
| --- | --- |
| 방이 옆으로 퍼진다 | 아이소메트릭 원근이 가로로 늘어난다. 지금 1.18 도 이미 18% 퍼진 상태다 |
| 도트가 정사각이 아니게 된다 | 픽셀 아트인데 가로 픽셀이 세로보다 굵어진다 |
| 소품도 같이 퍼진다 | 칸은 덮지만 침대·턴테이블의 형태가 변한다 |
| 강아지가 상대적으로 작아진다 | 개는 안 늘어나니 방이 넓어질수록 방 대비 작아 보인다 |
| 창밖이 늘어난다 | 창문·문도 `stage` 백분율이라 같이 퍼진다 |

**늘림 비율이 폰마다 달라진다는 것도 알아 둘 것.** 한계에 닿을 때까지만 먹으므로,
`H_STRETCH = 1.53` 이면 기준 기기는 1.53배(53% 퍼짐)인데 Pixel 7 은 1.14배(14%)다.
폭은 둘 다 꽉 차지만 **모양은 다르다.**

### 거절한 안

- **방 크기에 상한(천장)을 둔다** — 처음 안이다. 통일은 되지만 **잘 나오는 폰을
  끌어내린다.** 기준 기기는 335dp 라 천장(360)에 안 닿아 **아무 변화도 없고**, Pixel 7 은
  452 → 360 으로 92dp 를 잃는다. 그리고 Pixel 7 의 방 폭은 이미 386.7dp(여백 25dp)로
  **STATUS 5번이 쫓던 시안에 거의 도달해 있다** — 상한은 그걸 되돌린다.
- **상자 높이 자체에 `heightIn(max=…)`** — 상자가 줄면 `flexRoom`(힌지 선에 딱 맞춘
  값)과 `homeScrolls`(상자 높이로 갈래를 고른다)의 전제가 흔들린다.
- **방을 화면 폭에 맞추고 모자라면 홈을 스크롤로** — 모든 폰에서 방 폭이 같아지는
  완전한 해결이지만 **홈이 항상 스크롤 화면이 된다.** `"스크롤 없음"` 이 지금 설계
  결정이고(`HomeScreen.kt:531`), **STATUS 「다음 결정」 5번이 이것을 기획 결정으로
  파킹해 뒀다.** 에이전트가 정할 자리가 아니다.
- **산책 요약 카드를 조여 상자를 키운다** — STATUS 16절에서 이미 재보고 접은 길이다
  (*"이득이 방 폭 7% 인데 터치 영역을 내주고, 그러고도 시안에 못 간다"*). 1·2 번이
  같은 종류의 일인데 **+21%** 가 나온 이유는 그때 못 본 두 곳(시즌 행 58dp · `FabLift`
  22dp)을 찾았기 때문이다.

## 5. 저장소 탭을 요약 + 전체보기로 접는다

### 무엇이 문제였나

`ui/storage/ChatSummaryRoute.kt:134` 가 `LazyColumn` **하나**에 세 섹션을 세로로 이어
붙인다. 그런데 **세 섹션이 다 자라는 것은 아니다.**

| 섹션 | 자라나 | 지금 |
| --- | --- | --- |
| 오늘의 케어 기록 | 오늘 하루치라 상한이 있다 (그룹이면 식구 수만큼) | 전부 펼쳐 그린다 |
| 진료비 | **안 자란다** | 이번 달 합계 · 마지막 방문 · 「전체보기 ›」 → `VetVisitsScreen` |
| 대화 보관함 | **무한히 자란다** | 요약을 전부 항목으로 펼친다 |

**진료비가 이미 답을 보여 줬다.** 요약으로 접고 자세한 건 전용 화면이 받는다. 그래서
기록이 쌓여도 저장소 탭이 안 길어진다. **대화 보관함만 그 규칙 밖에 있고, 하필 목록
맨 끝이라** 스크롤 전체를 끌고 늘어난다.

덤으로, 지금은 요약을 보려면 항상 케어·진료비를 지나쳐야 해서
`animateScrollToItem(index + HEADER_ITEMS)` 같은 코드가 있다 (`:122`, `HEADER_ITEMS = 3`).
**머리 항목 수를 손으로 세어 맞추는 코드**라 섹션을 하나 넣을 때마다 밟을 자리다.

### 어떻게 정했나 — 진료비 패턴을 세 섹션에 다 적용

```
오늘의 케어 기록    오늘 챙긴 것 요약        → 전체보기 (날짜별)   ← 새 화면
진료비             이번 달 · 마지막 방문     → 전체보기            ← 이미 있음
대화 보관함        최근 2~3건               → 전체보기            ← 새 화면
사진               준비 중
```

- **탭 높이가 내용과 무관하게 고정된다.** 기록이 천 건이어도 저장소 탭은 그대로다.
- **이 저장소가 이미 고른 답**을 따르므로 새 개념을 안 만든다. `VetVisitsScreen` 이
  본보기라 형태도 이미 있다.
- `HEADER_ITEMS` 와 손으로 세는 스크롤 계산이 **사라진다** — 선택된 요약으로 가는
  동작은 전체보기 화면으로 옮겨가고, 거기선 목록이 하나뿐이라 셀 게 없다.

⚠️ **저장소 탭의 지금 높이는 재지 않았다.** 실제 케어·진료비 기록이 화면에 뜨는
자리라 사용자 허락 없이 열지 않았다. "스크롤이 얼마나 줄어드나" 는 **구현 때 실기기에서
확인한다.**

### 거절한 안

- **저장소 안에 하위 탭 셋** — 도감이 이미 탭 셋(야채·과일·포토)이라 같은 장치가 앱에
  두 벌 생긴다. 그리고 **저장소를 열면 무엇을 보러 왔는지 먼저 골라야 한다** — 지금은
  열면 한눈에 다 보이는데 그 성질을 잃는다.
- **섹션 접기(아코디언)** — 접힌 상태를 기억해야 하고, 기본값을 무엇으로 두든 누군가는
  매번 펼친다. 사용자에게 정리를 떠넘기는 방식이다.

## 6. 알림

### 지금 있는 것

사용자를 부르는 알림이 **하나** 있다 — 보행 분석 완료 (`gait/work/GaitAnalysisWork.kt:155`).
그리고 그것이 잘 만들어져 있어서 **본보기가 이미 저장소 안에 있다.**

```
채널 분리      "한 채널에 묶으면 사용자가 둘 중 하나만 끄지 못한다"  (walk_tracking ≠ gait_analysis)
권한 확인      areNotificationsEnabled()
SINGLE_TOP    "CLEAR_TOP 을 주면 보던 화면이 홈으로 초기화된다" — 앱을 앞으로만 데려온다
어디로 갈지    putExtra(EXTRA_OPEN_GAIT_RECORD, …)
중복 방지      notify(id = recordId.hashCode()) — 다시 돌아도 같은 자리에 덮어쓴다
색            setColor(BrandPrimary)   ⛔ docs/design-locks.md 0절
```

`POST_NOTIFICATIONS` 권한은 이미 선언돼 있고(`AndroidManifest.xml:28`) 두 곳에서
요청한다 (`ui/walk/WalkRoute.kt:172` · `ui/chat/ChatScreen.kt:640`).

### 무엇을 알리나 — 이 카드에서는 둘

처음에 사용자가 고른 것은 다섯(5 · 6 · 8 · 13 · 14)이었는데, **작업 중에 둘로 줄였다** —
*"5,8번 만 하자니까"*. 나머지는 빼는 것이 아니라 **뒤로 미룬 것**이다.

| # | 알림 | 어디에 붙나 | 이 카드 |
| --- | --- | --- | --- |
| 5 | 보행 분석이 끝났어요 | `GaitAnalysisWork` — **이미 있음** | ✅ 공용 자리로 옮김 |
| 8 | 산책 일기 장면이 준비됐어요 | `WalkDeliveryWorker` | ✅ 새로 붙임 |
| 2 | 오늘 아직 안 나갔어요 | 새 `notify/WalkReminderWork.kt` | ✅ 나중에 추가됨 |
| — | 포토 카드가 완성됐어요 | 새 `dogcard/photo/PhotoCardWatch.kt` | ✅ 나중에 추가됨 |
| 6 | 산책 기록을 못 보냈어요 | 같은 Worker 의 `Result.failure()` | 미룸 |
| 13 · 14 | ○○의 생일 · 가족이 된 날 | 새 일일 Worker + 강아지 정보 | 미룸 |

**포토 카드는 후보 목록에 없었다.** 사용자가 알림을 눈으로 확인하려고 꺼냈는데
(*"확인해보게 포토 카드 생성 시 알림뜨게 해줄 수 잇어?"*), 코드를 보니 **이미 약속만 하고
안 지키던 자리**였다 — 만들기 화면에 「다 되면 알려 주세요」 버튼이 있는데 그것이 하는
일은 화면을 닫는 것뿐이고, 폴링은 `repeatOnLifecycle(STARTED)` 안에 있어서 **앱을 내리면
멈춘다.** 서버가 30~60초 그리는 동안 나가면 알려 줄 사람이 없었다. 보행 분석과 같은
모양이라 Worker 로 뺐다.

⚠️ **앱이 앞에 있어도 띄운다.** 만들기 화면을 보고 있으면 뒤집기 애니메이션과 알림이
같이 온다. 보행 분석도 그렇게 돈다 — 앞/뒤를 따져 가리면 화면은 떠 있지만 다른 탭을
보고 있던 사람이 완성을 모르고 지나간다. 조회는 15초 간격이다(화면이 5초마다 이미 묻고
있어서 같은 간격으로 두면 서버에 두 배로 묻는다).

사용자는 처음에 **리마인더를 다 뺐다** (카드 충전 · 저녁 산책). 앱이 조르지 않는 쪽이다.
그런데 2번만 다시 들어왔다 — *"2번만 추가하고 싶은데 단순 매일 특정 시각 때 말고 뭔가
기존 산책 기록들 보고"*. **부르는 시각을 앱이 정하지 않는다면** 잔소리가 아니라는 것이다.

### 후보 2 — 「오늘 아직 안 나갔어요」

규칙은 `notify/WalkReminderRule.kt` 에 순수 함수로 있고, 테스트 15개가 잡는다.

| | 값 | 왜 |
| --- | --- | --- |
| 보는 기간 | 최근 **4주** | 요일이 네 번씩 들어온다 |
| 평소 시각 | 산책 시작 시각의 **중간값** | 평균은 새벽 산책 한 번에 끌려간다 |
| 여유 | **+1시간** | 평소 시각 정각에 부르면 준비하는 사람을 재촉하는 것이 된다 |
| 습관의 최소 | 4주에 **4회**(주 1회) | 이보다 드물면 「평소」가 없다 |
| 통금 | **21시** | 늦은 알림은 나가게 못 만들고 잠만 깨운다 |

**요일은 구분하지 않는다.** 사용자가 정했다 — *"요일 구분없이 가자"*. 주말에 늦게 나가는
집이면 평일 시각으로 부르는 셈이지만, 요일별로 가르면 4주에 요일당 네 번이라 최소 횟수를
채우는 집이 거의 없어진다. 규칙이 정교해지는 대신 **아무한테도 안 뜨는** 알림이 된다.

⚠️ **밤늦게 나가는 집은 아예 안 부르게 된다.** 평소 23시면 여유를 더해 자정을 넘고 통금에
걸린다. 그대로 둔다 — 자는 사람을 깨우는 것보다 낫고, 그 집은 어차피 늦게라도 나간다.

**작업이 둘이다.** 부를 시각이 집집마다 달라 「매일 9시에 도는 작업」 하나로는 안 된다.
`walk-reminder-plan`(12시간 주기)이 **언제 부를지 계산해** `walk-reminder-check` 를 그
시각에 예약하고, 그것이 깨어나 **한 번 더 확인하고** 부른다. 하나로 합쳐 스스로 다시
예약하게 하면 같은 고유 이름을 `REPLACE` 로 넣는 순간 **돌고 있는 자기 자신이 취소된다.**

예약한 뒤에 나갔을 수 있어서 `check` 가 다시 본다. 예약은 몇 시간 전에 걸렸고, 그 사이에
산책이 끝났으면 이 알림은 거짓말이 된다.

⚠️ **로그인하지 않았으면 기록을 안 읽는다.** 세션 행의 `ownerId` 는 로그인 전에 빈
문자열이라(`WalkSessionRow` 기본값), 빈 소유자로 거르면 **다른 사람이 이 기기에서 걸은
산책과 섞인다.** 기기를 물려받았거나 계정을 바꾼 경우다.

너무 짧은 산책은 걸러 낼 것이 없다 — 산책이 끝날 때 `WalkHistory.keepIfWalk` 가 이미
지운다 (50m · 60초 미만, 사용자가 기록을 남긴 것은 제외).

⚠️ **8번은 `Result.success()` 가 아니다.** `syncPendingSession` 은 `Unit` 을 돌려주고,
장면은 서버가 `ready` 를 줬을 때 로컬 DB(`WalkSceneAnalysisRow`)에 들어간다 — 서버가 아직
`running` 이면 **성공하고도 장면이 없다.** 그래서 왕복 전후의 `status` 를 비교해서 이번에
준비된 것만 알린다 (`notify/WalkDiaryNotice.kt` 의 `diarySceneBecameReady`). 전달 작업은
네트워크가 돌아올 때마다 다시 돌 수 있어서, 상태만 보고 띄우면 **장면 하나로 알림이 여러
번 뜬다.**

### 채널

성격이 다르면 나눈다 — `GaitAnalysisWork.ensureChannel` 주석의 그 규칙이다. 지금 붙인
둘은 **성격이 같다**: 기다리던 것이 준비됐다고 한 번 부르는 알림이다.

| 채널 id | 이름 | 중요도 | 알림 |
| --- | --- | --- | --- |
| `result_ready` | 완성 알림 | DEFAULT | 5 · 8 · 포토 카드 — 기다리던 것 |
| `walk_reminder` | 산책 알림 | DEFAULT | 2 — **앱이 먼저 말을 거는 것** |
| ~~`sync_problem`~~ | 보내지 못한 기록 | — | 6 과 같이 미룸 |
| ~~`anniversary`~~ | 기념일 | — | 13 · 14 와 같이 미룸 |

**2번을 완성 알림과 한 채널에 두지 않는다.** 부탁하지 않은 말은 끄고 싶을 수 있고, 그때
기다리던 결과까지 같이 꺼지면 안 된다. 실기기에서 안드로이드 알림 설정에 「완성 알림」 ·
「산책 알림」 · 「산책 기록」 셋이 각각 스위치를 달고 뜨는 것을 확인했다.

**채널 id 를 두 번 바꿨다.** `gait_analysis` → `analysis_result` → `result_ready` 다.
산책 일기가 들어오며 `gait_` 가 좁아졌고, 포토 카드는 **분석이 아니라 생성**이라
`analysis_` 도 좁아졌다. 이 저장소는 이름표와 하는 일이 어긋난 채로 두지 않는다
(`BottomTab.Storage` 주석). **아직 출시 전이라** 옛 채널을 지워도 잃을 사용자 설정이
없다 — 출시 뒤라면 못 한다. 지우면 사용자가 거기 해 둔 소리·중요도 설정이 같이 없어진다.
지울 옛 id 는 `LEGACY_CHANNEL_IDS` 에 **둘 다** 적혀 있다.

**채널은 `DaengsApp.onCreate` 에서 만든다.** 알림을 띄우는 순간에 만들어도 늦지는 않지만,
그러면 첫 알림이 뜨기 전까지 안드로이드 알림 설정에 **끄고 켤 항목이 하나도 없다** —
종 아이콘으로 거기까지 간 사용자가 빈 화면을 본다.

### 종 아이콘 = 알림함

지금 `onBell = {}` 라 **눌러도 아무 일이 없는 버튼**이 상단바에 있었다.

처음에는 **안드로이드 알림 설정**으로 보냈다 — 채널이 하나뿐인데 앱에 스위치를 또 두면
시스템과 어긋날 수 있다는 판단이었다. 실기기에서 보고 사용자가 바로 짚었다: *"지금 벨
모양 누르면 알림 설정창으로 가는데, 여기에 알림이 있으면 불이 들어오고 그 내용이
떠야하는거 아니야?"*. **맞는 말이다** — 종은 「설정」이 아니라 「알림 목록」이라는 뜻이고,
시스템 그림자에서 한 번 밀어 낸 알림은 다시 볼 곳이 없다.

그래서 **알림함을 만들었다** (`notify/NoticeInbox.kt` · `ui/notify/NoticeInboxScreen.kt`).

```
알림                                    다 지우기
  포토 카드가 완성됐어요.                     ●     ← 안 읽음
  도감에서 뒤집어 보세요.
  오전 12:13
  산책 일기 장면이 준비됐어요.
  오늘 산책을 일기로 남겨 보세요.
  어제 오전 11:53

  알림 설정                                  ›     ← 시스템 설정으로 가는 길은 남긴다
```

- **안 읽은 것이 있으면 종에 점이 뜬다.** 숫자는 안 붙인다 — 「3」이 뜨면 세 개를 다
  처리해야 할 것처럼 보이는데, 이 알림들은 처리할 일이 아니라 소식이다.
- **목록을 열면 전부 읽음이 된다.** 줄마다 읽음 표시를 두면 사용자가 관리할 것이 하나
  늘어난다. 점은 **열던 순간의 것으로 고정**해서, 이번에 새로 온 것이 무엇이었는지는
  보이게 한다 (살아 있는 값으로 그리면 점이 뜨자마자 사라진다).
- **권한이 꺼져 있어도 여기엔 남는다.** `postDaengsNotice` 가 **목록에 먼저 적고** 시스템
  알림을 띄운다. 사용자가 끈 것은 *시스템이 부르지 마라* 였고 *앱에서도 숨겨라* 가 아니다.
- **누르면 알림을 누른 것과 같은 자리로 간다.** 실어 나르는 값(`extras`)도 같은 열쇠라,
  `MainActivity` 가 한 군데서 해석한다 — 두 길이 갈라지면 같은 알림이 그림자에서는
  일기로, 목록에서는 홈으로 가는 일이 생긴다.
- 저장은 SharedPreferences 다. 최근 30개만 들고 있고 조회 조건이 없어서 Room 이 할 일이
  없다 (`RoomStore` · `PhotoRevealLog` 와 같은 계열).

**앱 안에 채널 스위치는 여전히 두지 않는다.** 켜고 끄는 것은 안드로이드가 채널마다
해 주고, 앱에 또 두면 **둘이 어긋난 상태**(앱은 켬, 시스템은 끔)가 생긴다 — 그러면
사용자는 켜져 있는 스위치를 보면서 알림을 못 받는다. 목록 맨 아래 「알림 설정」이
거기로 보낸다.

⚠️ 그래서 **권한 요청도 이 카드에 없다.** 스위치를 켜는 순간이 없다. 지금은 산책과
챗에서 요청한다 (`ui/walk/WalkRoute.kt:172` · `ui/chat/ChatScreen.kt:640`).

### 공용 헬퍼

`GaitAnalysisWork.notify()` 의 패턴을 `notify/DaengsNotifications.kt` 로 빼고 다섯이
그것을 쓴다. **후속 알림이 각 3~5줄이 되는 것이 이 작업의 목적이다.**

### 안 넣은 것

- **9. 피부 진단 결과** — 사용자가 뺐다. 진단이 `ui/chat/AssistantChat.kt` ·
  `ChatScreen.kt` 의 **화면 스코프**에 있어서, 알림을 붙이려면 먼저 Worker 로 옮겨야
  한다. 보행 분석은 이미 옮겨져 있는데(`GaitAnalysisWork` + `GaitPendingWatches` +
  `GaitWatch`) 피부 진단은 안 옮겨졌다 — **같은 성질의 일인데 처리가 갈려 있고, 지금은
  진단 중에 화면을 나가면 결과를 잃을 수 있다.** 별도 카드가 필요하다.
- **푸시(FCM)** — 탈취 알림 · 식구의 기록 · 그룹 초대. `DAENGS_dev` 에 FCM 키 · 토큰
  등록 API · 발송 로직이 먼저 있어야 한다. **저쪽 저장소 작업이 선행 조건이다.**
- **알림함** (기기에 쌓인 알림 목록) — Room 테이블 + 목록 + 읽음 상태 + 배지라 별도
  카드 크기다. 그리고 **그 값은 푸시가 생긴 뒤에 커진다** — 로컬 알림 다섯뿐이면
  안드로이드 알림 그림자로 충분하다.
- **배웅한 아이를 기억하는 날** — 이 앱은 배웅을 삭제와 다르게 편지와 하트로 아주
  조심스럽게 다룬다 (`HISTORY` · PR #76~#80). 알림이 그 결을 깨뜨릴 수 있고 **예고
  없이 오면 상처가 된다.** 넣더라도 기본 꺼짐 + 사용자가 직접 켜는 것이어야 하고,
  그건 사용자와 한 번 더 이야기할 자리다.

## ~~7. `+` 편집에서 날짜·이름표 자리를 고른다~~ — 안 한다

**2026-09-18 에 사용자가 작업에서 뺐다.** 날짜 카드와 이름표는 **지금 자리 그대로
고정**이다 — `TodayCard` 는 방 상자 `TopStart` 에 12/10dp, 이름표는 방 그림 기준
`NamePlateSpec.BOTTOM = 102%` 다.

되살릴 일이 생기면 여기서 이어 간다. 설계는 **자리 고르기(스냅)** 였다 — 자유 드래그가
아니라 방 그림 기준 자리 다섯 개(위오른쪽은 `+`·`DEV` 가 써서 제외) 중 하나로 붙이고,
이미 찬 자리에 놓으면 둘이 **자리를 바꾼다.** 자유 드래그를 거절한 이유가 핵심이다 —
이름표 가로를 백분율로 저장하면 *"이름이 길어질 때 한쪽으로 밀린다"* (`HomeScreen.kt:112`
가 이미 거절한 방식이고), `TodayCard` 는 접었다 펴면 높이가 변하며, 방 크기가 기기마다
달라 작은 폰에서 두 카드가 겹친다.

## 검증

**모션과 그림은 테스트로 못 잡는다** (`CLAUDE.md`: *"테스트는 좌표·배치·규격을 잡는다.
그림이 예쁜지는 못 잡는다"*). 그래서 이렇게 가른다.

### 테스트가 잡는 것

| 무엇 | 어떻게 |
| --- | --- |
| 하단바 규격 | 새 `HomeBottomBarLockTest` — `FabSize` · `FabLift` · `BarHeight` · 시즌 행 높이 |
| 방 크기 상한 | 기기 크기 여러 개를 `RoomGeometry.of` 에 넣어 상한을 안 넘는 것 |
| 카드 자리 | 자리 5개 × 기기 크기 몇 개로 **카드가 방 그림 밖으로 안 나가는 것** |
| 전환 스펙 | 순수 함수 — 총 300ms, 나가는 쪽이 들어오는 쪽보다 먼저 끝남 |
| 인벤토리 슬롯 | 슬롯이 필요한 높이를 받는 것 (지금 깨진 그 자리) |
| 기념일 판정 | 생일이 빈 강아지를 건너뛰는 것, 오늘 판정 |
| 저장소 요약 | 섹션이 요약만 그리고 목록 길이와 무관하게 높이가 고정인 것 |

### 실기기가 잡는 것

- 1·2 의 최종 숫자 — 시즌 행이 바에 붙은 느낌, 동그라미 크기
- 4 의 상한 360dp — 큰 폰에서 공기가 어색하지 않은지
- 3 의 모션 — `adb shell screenrecord` 로 녹화해 프레임 시트로 본다
- 5 의 스크롤 감소량 — 실제 기록이 있는 계정에서
- 6 의 알림 — 실제로 뜨는지, 눌렀을 때 보던 화면이 안 날아가는지

⚠️ `adb install` 출력에 `Success` 가 뜨는지 **직접 본다** (`CLAUDE.md`).

## 열린 질문

- **시즌 행 ↔ 흰 바 11dp** 가 좁으면 `Spacer` 를 4~6dp 로 되돌린다. 실기기 확인 후.
- **방 상한 360dp** — 큰 폰에서 봐야 안다. 상수 하나.
- **7번 자리 목록에 위왼쪽이 들어가는지** — 사용자가 "위가운데 · 아래왼쪽 · 아래가운데 ·
  아래오른쪽만 해도 돼" 라고 했다. 위왼쪽은 날짜의 기본 자리라 빼면 기본 배치가 바뀌므로
  **포함으로 읽었다.** 아니면 넷으로 줄인다.
