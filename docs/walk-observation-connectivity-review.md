# 보행 제외 관측의 연결 근거 대조

2026-09-12 · APP #338 · `legacy-observation-review-v1` · **검토 후보**

완료 기록을 검토 앱에서 열면, 기존 보행선 밖의 관측을 연결할 근거와 보류한 이유를
`report.json`에 추가한다. 기존 지도·장면 대응·거리·활동시간은 유지한다. 지도 채택은
다음 단계다. A/B는 [실제 기록 대조](walk-real-record-review.md)의 동일 입력이다.

## 입력과 책임

`evaluateLegacyObservationConnections`는 완료된 legacy 읽기의 원본을 `clientSeq` 순서로
평가하는 순수 함수다. `LegacyRouteEvidence.matches`로 동일 summary 객체·경로·원본을
검사한다. 미완료 기록, 뒤집힌 기록 시간, 음수/중복 원본 주소, motion 측정, 근거 없는
읽기는 `unsupported_reason`을 반환한다. 누락 순번은 연결 미확정으로 남긴다.

입력 범위는 **현재 제공된 legacy 관측**이다. 완료 시각이 있다고 백업 완전성이나
업로드 receipt까지 확인된 것은 아니다. `input_scope=provided_legacy_observations`를
명시하며 신규 motion 정책이나 서버의 활성 측정으로 대체하지 않는다.

| 축 | 결과 | 의미 |
|---|---|---|
| 위치 품질 | USABLE / UNCERTAIN / INVALID | 좌표·정확도·mock 여부에 따른 사용 가능성 |
| 관측 연결 | CONNECTED / BROKEN / UNRESOLVED | 인접 원본을 후보 정책에서 연결할 근거가 있는지 |
| 기존 보행 집계 | INCLUDED / EXCLUDED / UNRESOLVED | 기존 수용 연결의 범위 소유권 또는 실제 제외 근거 |
| 보조 경로 사용 | REVIEW_CANDIDATE / RESERVED_BY_WALKING / OWNERSHIP_CONFLICT / UNAVAILABLE | 앞의 결과로부터 얻은 표시 후보 자격 |

`CONNECTED`는 위치의 연속성 후보다. 실제 이동·정지 판정, 방향 화살표, 사건 당시 위치까지
보장하지 않는다. 작은 흔들림이 연속돼도 이동거리나 정지 시간을 새로 만들지 않는다.
연결할 근거가 없는 점도 원본 위치와 품질·시간을 유지한다.

## 거리 소유권 보존

`TrailRecorder`의 기존 수용 분기가 실제로 더한 거리 기여를 `TrailDecision`에 함께 출력한다.
`LegacyRouteEvidence`는 정상 장면에 안전한 연결의 부분집합과 **모든 실제 수용 연결**을
따로 보관한다. 수용 정책·거리 계산식·필터 상태는 바꾸지 않는다.

수용점 B → 제외점 X → 수용점 C에서 기존 reader가 B→C를 집계했다면, B→X와 X→C의
원본 범위는 B→C 한 개가 소유한다. 이 안에 보조 경로를 더하지 않는다. 제외점이나
미확정 연결이 들어 있는 기존 소유 범위는 `OWNERSHIP_CONFLICT`로 보고한다.

`INCLUDED`는 **원본 범위의 소유권**이다. 그 안의 모든 원본 선분을 보행으로 인정하거나
각 선분 길이를 합산했다는 뜻은 아니다. 거리 기여는 `owners`에 한 번만 있다.
원본 구간에는 `owner_to_seq`만 연결하고 기여를 복사하지 않는다. 소유 범위 중첩은
실패로 처리하며 소유자가 있는 구간은 보조 후보가 될 수 없다.

소유자가 없고 실제 도착 관측이 고속/저정확도/기록 제외 판정을 받았거나 recordingEligible이
false이면 EXCLUDED다. 소유자가 없다는 이유만으로 제외로 확정하지 않는다. 짧은 정지
흔들림 등은 UNRESOLVED일 수 있다. 공백과 제외는 서로 다른 축으로 유지한다.

## 후보 정책과 근거

아래 값은 리뷰용 공학적 가정이다. Android 표준이나 실세계 검증을 끝낸 제품 기준이 아니다.
#470의 20초/200m를 이식하지 않았으며 A의 특정 장면을 연결하도록 상수를 조정하지 않았다.
정책 식별에는 버전과 **전체 매개변수**를 함께 사용한다. 같은 버전의 민감도 변형을
같은 판정 정책으로 취급하면 안 된다.

| 매개변수 | 기본값 | 역할 |
|---|---|---|
| 최대 보고 정확도 반경 | 25m | 반경이 없거나 더 크면 위치 품질 미확정 |
| 최소 인접 관측 간격 | 500ms | 너무 짧은 차분 속도 판단 보류 |
| 최대 인접 관측 간격 | 10초 | 작은 위치 차이여도 긴 시간 공백은 연결 보류 |
| 정확도 여유를 뺀 최대 속도 | 35m/s | 보행 상한과 별도로 좌표 도약 점검 |
| 이웃 속도 벡터 변화 계수 | 8m/s² | 속도 크기만으로 통과하는 튐·즉시 복귀 점검 |
| 일관된 최소 연속 구간 수 | 3개(관측 4개) | 두 점만으로 연속 경로를 확정하지 않기 |
| 단조/일반 시각 간격 차이 | 1초 이내 | 시각 근거의 불일치 보류 |

인접 원본의 시간 `dt`, 거리 `d`, 양 끝 보고 정확도 반경 합 `r`에 대해
`coordinateSpeed=d/dt`, `adjustedSpeed=max(0,d-r)/dt`를 기록한다. 기존 recorder의
마지막 **수용점** 기준 속도와 구분하고 `speed_source=adjacent_raw_coordinates`를 명시한다.
연속 두 구간의 방향을 포함한 속도 벡터 차이가 다음 allowance보다 크면 **두 구간 모두**
미확정으로 남긴다. 그 뒤 남은 연결 블록에 최소 연속 구간 수를 적용한다.

```text
allowance = 8 × (dt₁ + dt₂) / 2 + r₁ / dt₁ + r₂ / dt₂
```

보고 반경을 활용한 휴리스틱이며 확률적 신뢰 구간이 아니다.
[Android Location 문서](https://developer.android.com/reference/android/location/Location)에 따르면
위치 정확도는 68% 반경 추정치이고 기기 제공 속도는 좌표 차분과 다른 근거를 쓸 수 있다.
따라서 위 식을 GPS 오차 상한이나 `getSpeed()` 복원으로 설명하지 않는다. 좌표 거리·벡터는
원본 이웃으로만 구하며 리샘플링·스무딩·도로 맞춤을 하지 않는다.

chain, source epoch, clock epoch, recordingEligible, 기록 시간 범위, 무효 위치의 경계는
BROKEN이다. 정확도 미확정, 순번 누락, 시간 오류/공백, 속도·이웃 불일치, 근거 부족은
UNRESOLVED다. 잘못된 관측을 삭제하고 앞뒤를 자동 연결하지 않는다.

단조 시각은 두 관측 모두에 있고 같은 명시적 clock epoch/source epoch에 속하며 증가할
때만 사용한다. 일부만 있거나 epoch 없는 단조 시각은 미확정이다. 둘 다 없으면
`LEGACY_WALL_TIME`의 제한된 근거를 명시한다. 일반 시각 중복·역전도 보류하고 바로 다음
나가는 구간까지 `UNTRUSTED_START_TIME`으로 격리한 뒤 후속 정상 관측에서 다시 평가한다.
관측 핀을 삭제하거나 시간 길이를 꾸미지 않는다.

### 매개변수 민감도

정확도 15/35m, 최대 간격 5/15초, adjusted speed 25/45m/s, 벡터 변화 계수 4/12m/s²,
최소 연속 구간 2/4개의 10개 변형을 기본값과 각각 대조한다.

- 정확도 15m: A는 8개 구간(최초 from seq 1), B는 7개(최초 0)의 판정이 바뀐다.
- 벡터 변화 계수 4m/s²: A는 2개 구간(최초 from seq 338)이 바뀌고 후보 시작이
  **339에서 340으로** 이동한다. B는 변하지 않는다.
- 나머지 변형은 이 두 입력의 연결 상태/보조 후보 자격을 바꾸지 않는다.

A의 꼬리 전체가 모든 기준에서 확정됐다는 결론은 내리지 않는다. 기본 경계 339→340은
후속 지도 채택 리뷰에 가져갈 항목이다. 같은 변화율 기준으로도 정상 급회전이 보류되거나
부드러운 GPS 드리프트가 통과할 수 있다. 독립적인 실제 경로 정답과 기기 속도 근거 없이
이 둘을 완전히 구분했다고 할 수 없다.

## 재현 및 검증

`report.json.observation_connectivity`에는 정책 전체, 위치별 원본 처리 사유, 거리 소유자,
인접 구간 판정/시각 근거/수치, 이웃 비교, 후보 범위, 전환, 장면 시간 관계, 민감도별 최초
차이가 있다. 읽기 쉬운 표는 네트워크 없이 생성한다.

```powershell
uv run --no-project tools/render_observation_review.py --report <private-capture>/report.json
# JVM 재생 결과 observation-replay-338.json도 같은 형식으로 읽는다.
```

원본 좌표·계정·장면 본문·폰 캡처와 전체 보고서는 개인 작업 공간에만 둔다. Git에는
정책 코드·합성 반례·비식별 결과만 넣는다. 이 보고서는 대용량 제품 API 설계가 아니다.

```powershell
.\gradlew.bat :app:assembleDebug :app:testDebugUnitTest `

  --tests '*LegacySceneBindingTest' --tests '*CompletedRouteReviewTest' `
  --tests '*TrailRecorderTest' --tests '*WalkSummaryTest' --tests '*WalkHistoryTest' `

  -I tools/walk-record-review.init.gradle -PslimAbi=arm64-v8a -PversionName=walk-review-338 --max-workers=2
```

- 11개 클래스 **102개 테스트 통과**, 실패·오류·skip 0, debug 빌드 통과.
- 안정된 빠른 관측, 정상→제외→재개와 소유 충돌, 일시정지, 큰 점프, 속도 상한보다 작은
  튐·복귀, 긴 시간 공백, 좌표/정확도/mock 오류, epoch, 시각 역전과 복구, 원본 주소 오류,
  두 점만 있는 경우, 작은 정지 흔들림을 합성 입력으로 검증했다.
- 같은 최종 원본의 저장/업로드 묶음을 바꿔도 순번 정렬 후 판정·소유·후보·전환이 같다.
  새로운 스트리밍 연결 평가기를 구현했다는 뜻은 아니다.
- 실제 A/B 입력과 장면 해시를 검증하고 #336 기준 거리·활동시간·장면 관계,
  기존 summary/경로, 거리 소유자 합을 대조했다. A 5·6의 후보 성공을 테스트 정답으로
  고정하지 않고 독립 합성 조건으로 정책을 검증했다.

SM-S931N에 별도 `walk-review-338`을 설치하여 `Success`를 확인했다. A/B를 서버에서
다시 조회했고 원본·장면 SHA-256은 #336과 같았다. 기기 보고서의 기존 모든 필드는
앱 버전·조회 시각을 제외하고 #336과 동일했다. A 3 / B 3의 선·방향 강조, A 5·6의
핀과 보행선 무강조를 화면에서 확인했다. 원래 앱 1.1.2의 업데이트 시각도 유지됐다.

기기와 JVM의 후보 상태·사유·원본 범위·정책·민감도 결과는 같다. 다만 전체 JSON의
수치까지 완전히 같지는 않다. A/B에서 이웃 속도 벡터 변화 값의 최대 절대 차이는 각각
약 1.54×10⁻⁹ / 1.44×10⁻⁹m/s, 개별 소유 거리 기여 차이는 각각 약 8.89×10⁻¹⁶m다.
좌표 거리/속도 일부에도 차이가 있다. 전체 차이를 개인 보고서에 남겼으며 임의의
허용오차를 추가해 결과 해시 일치나 수치 동등성을 선언하지 않았다. 같은 입력의 기존
총거리 보존과 후보 판정 일치는 이 수치 차이와 별도로 확인했다.

## 다음 지도 단계의 계약

보조선은 같은 읽기 근거와 정책 전체가 확인된 후보 범위에서만 준비한다. 기존 보행 소유
범위나 공백을 건너 만들지 않는다. 선택 스타일은 보행 제외/미확정의 의미를 유지하고,
방향은 선택된 방문 주변의 이동 근거를 추가로 확인해야 한다. 위치 연속성만으로 화살표를
자동 허용하지 않는다. 장면 6은 사건과 마지막 위치의 시각 차이를 그대로 전달한다.

정책 채택·보조선 UI·시작/종료 문맥·전체 기록 카메라는 아직 완료되지 않았다.
B의 원래 270m와 확보 입력의 271.531737m 차이, 실제 다중 구간/공백 검증, 완전한 motion
기록을 이용한 API→APP 전환도 별도 항목으로 유지한다.
