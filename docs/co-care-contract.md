| 구분 | 기능 | 지금 상태 |
| --- | --- | --- |
| **공유** | 밥 · 약 · 간식 케어 기록 | 구현 |
| **공유** | 산책 기록 | 구현 — 「산책별」에 수행자 배지로 합쳐 보인다 |
| **공유 (계약)** | 진료비 영수증 | **미구현 — 고도화** |
| 비공유 (실행자 개인 기록) | 보행 분석 · 피부 검사 | MVP 에서 공유하지 않는다 |
| 비공유 | 챗봇 대화 · 카드 뽑기 · 산책 모아보기 · 산책 게임 | — |

- 개인 기록은 나가기 · 내보내기와 무관하게 실행한 사람이 계속 소유한다.
- 나가기 · 내보내기 뒤 공동 돌봄 중 보이던 공통 정보는 **자기 원본 강아지 값으로 돌아간다**(복사하지 않는다). 안내는 #440.

**지금 구현과 계약이 다른 자리 (코드 변경 보류):**

- 보행 · 피부 검사는 서버가 강아지의 구성원에게 조회 · 생성을 열어 두었고, 아래 ② 표도 그 구현(돌보미의 보행 · 스크리닝 **촬영**을 가리지 않음)을 따른다. 계약은 실행자 개인 기록이다.
- 진료비 영수증은 **공유되지 않는다.** 저장소 탭 진료비 영역은 **대표 강아지** 기준인데, 연결 없이 참여한 돌보미가 함께 돌보는 아이를 대표로 두면 목록이 404 라 "진료비 기록을 불러오지 못했어요"로 보인다. 자기 강아지를 대표로 두면 정상이다. 여러 마리 분할 확정은 함께 돌보는 아이도 후보로 보여 주지만 고르면 확정이 실패한다. 자세한 현재 동작과 고도화 방안은 서버 `docs/vet-visits.md` 「공동 돌봄」.

## ① 새로 만들 화면 — 지금 앱에 아예 없는 기능

| 엔드포인트 | 화면 | 권한 |
| --- | --- | --- |
| `POST /app/pets/{id}/invites` | 초대 링크 만들기 → 카톡 공유 | 대표만 |
| `GET /app/pets/{id}/members` | 보호자 목록 (대표가 맨 앞) | 구성원 |
| `DELETE /app/pets/{id}/members/{uid}` | 내보내기 / 나가기 | 대표 또는 본인 |
| `POST /app/pets/{id}/owner` | 대표 넘기기 | 대표만 |
| `GET /app/pets/{id}/invites` · `DELETE /app/pets/{id}/invites/{iid}` | 초대 목록·취소 (⑥에서 추가돼 배포됨) | 대표만 |
| `POST /app/pet-invites/accept` | **딥링크 수신 → 수락** | 로그인 사용자 |

**딥링크 처리가 필요하다.** 초대 생성 응답의 평문 토큰은 **그때 한 번만** 나온다 — 서버는
해시만 갖고 있어 다시 못 보여 준다. 링크는 24시간·일회용이고, 한 아이에 살아 있는 초대는
최대 3개다.

수락 경로에 `pet_id` 가 **없는 것은 의도다.** 수락 전에는 그 아이에 아무 권한이 없어서,
경로나 본문에 아이 id 를 실으면 남의 아이 id 를 넣어 보는 자리가 생긴다. 토큰만 보낸다.

## ② 안 고치면 버그처럼 보이는 자리 셋

### `PetResponse.is_owner` (기본값 `true`)

이제 **`GET /app/pets` 에 돌보미로 참여한 아이도 섞여 온다.** 둘을 가르는 것은 이 값뿐이다.
안 보면 돌보미 화면에 대표 전용 버튼이 그대로 뜨고, 누르면 404 가 난다.

가리는 것과 아닌 것이 갈린다:

| | |
| --- | --- |
| **가린다** | 강아지 프로필의 수정 · 배웅 · 삭제 · 사진 변경 |
| **가리지 않는다** | 밥 · 약 · 간식 기록, 보행 **촬영**, 스크리닝 **촬영**(아이를 지정했을 때) |

**`is_owner` 는 강아지 프로필에만 쓴다.** 보행·스크리닝의 **확정·삭제는 서버가 주는
`can_confirm`·`can_delete`** 로 가른다 — 보행 확정은 **업로더 또는 대표**라 `is_owner`
하나로는 못 가리고(돌보미의 촬영이 마지막 걸음에서 막힌다), 스크리닝 확정은 **창작자
전용**이라 대표조차 못 한다. 자세한 것은 ⑥.

돌보미는 **기록하고 본다.** 되돌리기 어려운 것만 대표 전용이다.

**스크리닝 확정은 `is_owner`로 가르면 안 된다.** 검토한 서버 구현은 기록을 **만든 사람만**
확정하도록 한다. 돌보미가 직접 촬영한 사진의 업로드 완료·판정 요청도 여기에 포함된다.
삭제는 창작자 또는 강아지의 대표다. 케어 기록 삭제도 작성자 또는 대표만 가능하다.
`is_primary`는 계정에서 선택한 대표 **강아지**, `is_owner`는 그 아이의 대표 **보호자**로
서로 다른 값이다. 대표 강아지 선택이나 방 표시 설정을 대표 보호자 전용으로 묶지 않는다.

### 마릿수 상한의 뜻이 바뀌었다

"내가 등록한 아이 수" 가 아니라 **"내 미니룸에 서는 아이 수"**(대표 ∪ 돌보미)다.
앱이 자기 소유만 세어 `+` 버튼을 보이면 서버가 409 를 낸다.

### 초대 수락은 재시도해도 된다 — 응답 코드가 셋으로 갈린다

초대 링크는 일회용이지만, **응답을 놓쳤을 때 같은 토큰으로 다시 보내는 것이 정답이다.**
서버가 초대 행을 `expires_at` 까지 보존하고 `accepted_at`·`accepted_by` 를 남기기 때문이다.

| 응답 | 뜻 | 앱이 할 일 |
| --- | --- | --- |
| **200** | 수락됐다. **같은 사람의 재시도면 첫 성공과 똑같은 `{pet_id, name}`** 이 온다 | 성공으로 그린다 |
| **404** | 없는 토큰이거나 **다른 사람이 이미 쓴** 링크다 | 잘못된 링크로 단정해도 된다 |
| **410 Gone** | **만료된 초대**다 (24시간). 대표가 바뀌어 무효가 된 초대도 여기다 | 새 초대를 받으라고 안내한다 |

**만료는 404가 아니라 410이다** — 둘을 한 문장으로 묶으면 "링크가 잘못됐다" 와 "시간이
지났다" 를 사용자에게 구별해 줄 수 없다.

**`GET /app/pets` 목록으로 수락 성공 여부를 추측하지 않는다.** 재시도가 200을 돌려주므로
추측할 이유가 없고, 목록에 돌보미 강아지가 있다는 사실은 다른 초대·다른 기기의 결과일 수
있어 애초에 근거가 못 된다.

## ③ 새로 생긴 409 셋 — 서로 다르다

| 상황 | 통과 방법 | 주의 |
| --- | --- | --- |
| 약을 6시간 안에 다시 기록 | body 에 `confirm: true` + **같은 `client_event_id`** | 새 키를 만들면 두 줄이 된다 |
| 돌보미 있는 강아지 삭제 | 쿼리 `?confirm=true` | body 가 아니다 |
| **탈퇴** | **`confirm` 으로 안 넘어간다** | 승계 / 내보내기 **두 출구**를 안내해야 한다 |

앞의 둘은 구조화된 dict `detail` 을 준다 — 누가 · 언제 · `nickname` 이 실려 오므로
"아빠가 08:15 에 줬어요" / "아빠도 맥스를 돌보고 있어요" 를 그릴 수 있다.

**세 번째를 앞의 둘과 혼동하면 안 된다.** 탈퇴 409 는 확인이 아니라 차단이다 — 대표를
넘기거나 돌보미를 내보내야 통과한다. `confirm` 을 붙여도 안 된다.

## ④ 응답이 바뀐 곳

- **케어 로그에 `actor` 가 붙는다** — `{app_user_id, nickname}`.
  **`nickname` 이 `null` 이면 "이전 보호자"로 그린다** (지금 구성원이 아닌 사람). 탈퇴했다가
  재가입한 사람의 새 닉네임이 옛 기록에 뜨는 것을 막는 장치라, 이 규칙을 그대로 따라야 한다.
- **하루 요약의 산책 수에 다른 보호자의 산책이 포함되고, `walk_rows` 로 누가 다녀왔는지도
  온다.** 앱은 저장소 탭 「오늘의 케어 기록」에 "산책 · 08:00 / 키키"(닉네임이 없으면 "이전
  보호자") 로 그린다. 산책 줄에는 지우기가 없다.
- ⚠️ **정정 (2026-09-15) — 산책 기록은 공동 조회한다.** 예전 이 자리의 "다른 보호자의 산책은
  `GET /app/walks` 목록에는 안 뜨고 요약의 숫자로만 보인다" 는 **MVP 결정(2026-09-12 §7·§11
  P0-11 「산책 공동 조회·수행자 표시」)보다 먼저 쓰인 문장**이고, 그 뒤 구현에서 빠져 있던 것을
  이번에 **기존 MVP 누락 보완**으로 채운다(서버 SAJOYO/DAENGS_dev#539, 앱 이 PR).
  - 서버: `GET /app/pets/{pet_id}/walks?cursor&limit`(목록, 좌표 없음) ·
    `GET /app/pets/{pet_id}/walks/{walk_id}`(상세 + 경로). 수행자·일시·시간·거리·`is_mine`.
  - **조회만 공유한다.** 산책의 소유·수정·삭제는 올린 사람의 `/app/walks` 그대로이고, 그 목록도
    여전히 내 산책만 준다. 앱은 공동 조회 결과를 기기 기록(Room)과 섞지 않고 산책 기록 화면의
    「함께 돌보는 보호자의 산책 보기」에서 따로 읽기 전용으로 연다(내 산책은 빼고 보여 준다).
  - 나가기·내보내기 뒤에는 서버가 404 를 준다. 공동 조회 전 서버(경로 없음)면 앱은 쓸 수
    없다고만 말하고 개인 산책은 그대로 돈다.
  - **게임·점령 결과 공유는 이번 결정으로 후순위 보류다** — 원래 의도에 포함돼 있었고, 처음부터
    제외된 요구사항이 아니다. 공동 조회 응답·화면에 넣지 않는다. 추후 고도화는 셋으로 나눈다:
    ① 산책별 게임·점령 결과의 읽기 전용 공유 ② 점령지·점수·보상 등의 공동 소유·집계
    ③ 그룹 가입·탈퇴가 게임 권한과 순위에 미치는 영향.
  - 산책 일기·행동 핀 공유는 이번 범위 밖이고 후속 확인 항목이다.
- **스크리닝**: 아이를 지정한 기록은 그 집 구성원에게 보이지만, **아이 없이 찍은 개인 기록은
  창작자만 본다.** 목록에도 상세에도 안 나온다. "아이 없이 찍은 사진도 우리 집 모두가 본다"
  고 가정하면 안 된다. 삭제는 **창작자 또는 대표** 둘 다 되고, 그 외 돌보미는 보이지만
  못 지운다(404).

## ⑤ 앱이 정해야 하는 것

**미니룸에 돌보미의 강아지를 세울 것인가.**

서버는 **세운다**는 전제로 상한을 구성원 기준으로 바꿨다(위 ②). 앱이 "내가 등록한 아이만
방에 세운다" 로 가면 그 전제가 깨지니, 정해서 서버 쪽에 알려 주면 맞춘다.

**A안으로 확정한다: 내가 돌보미로 참여한 아이도 내 미니룸에 기본 표시한다.** 다른 보호자가
키우는 모든 아이를 가져오는 것이 아니라, 내가 초대를 수락해 구성원이 된 아이만 포함한다.
마이 목록에서는 이름 옆 **「공동 돌봄」 배지**로 대표 보호자 소유 아이와 구분한다.

근거는 [HISTORY 22절](../HISTORY.md#22-5마리는-재서-정한-숫자다-08-31)과 현재
`ui/home/RoomRoster.kt`다. 홈은 서버 강아지 목록을 방 명부로 바꾸고, `PetHolder.canAddMore`도
목록 전체와 서버 `max_pets`를 비교한다. 소유자 필터를 새로 넣지 않는 A안이 이 구조를 따른다.

다만 **방에 보이는 수와 서버 상한은 정확히 같은 값이 아니다.** 기존 `roomPets`는 사용자가
숨긴 아이를 표시에서 제외한다. 숨기기는 내 방의 표시 설정일 뿐 공동 돌봄 나가기가 아니며,
숨긴 아이·배웅한 아이도 서버 구성원 상한에 포함한다. 숨겨서 등록·수락 가능 자리가 늘어나지
않는다. 방 격자는 현재 `RoomSpec.GRID = 12`이며 과거 기획의 6×6으로 되돌리지 않는다.

## ⑥ 서버와 합의한 계약 — **반영·배포 완료**

계약을 대조한 기준은 서버 [#388의 `1bf2d57`](https://github.com/SAJOYO/DAENGS_dev/pull/388)
이었고, **네 건 모두 서버에 반영되어 `4de11e6` 로 머지·배포됐다.** 아래에 "합의했다" 로
적힌 문장은 전부 지금 살아 있는 동작이다.

**앱 모델이 따라야 할 실제 응답 모양** (배포된 `schemas/*.py` 기준):

| 필드 | 모양 | 주의 |
| --- | --- | --- |
| 보행·스크리닝 `created_by` | **문자열 이름표** (`str \| None`) | `{app_user_id, nickname}` 객체가 **아니다.** 객체로 읽으면 조용히 null 이 되어 작성자가 사라진다 |
| 케어 로그 `actor` | 객체 `{app_user_id, nickname}` — **두 칸 다 null 가능** | 옛 기록·탈퇴자는 `{null, null}` 로 온다. `actor` 자체를 생략하지는 않는다 |
| 구성원 목록 `MemberOut` | `{app_user_id(필수), nickname, is_owner}` | 이쪽 `app_user_id` 는 non-null 이다. 케어 `actor` 와 **같은 타입으로 묶지 않는다** |
| `can_confirm`·`can_delete` | bool | 보행은 확정이 `PENDING` 일 때만, 스크리닝은 `PENDING_UPLOAD` 일 때만 true 다 |

### 초대 수락 성공을 복구할 식별 정보 — **해결됨**

**옛 동작(문제):** 수락 요청은 토큰뿐이고 성공 응답은 `{pet_id, name}`인데 서비스가 성공 시
초대 행을 지웠다. 첫 응답을 잃고 재시도하면 404라, 앱에는 토큰과 어느 강아지가 연결되는지
알 수단이 없었다. 전후 목록 차이도 다른 초대·기기에서의 변경과 구분되지 않았다.

**지금 동작:** 서버가 초대 행을 `expires_at`까지 보존하고 `accepted_at`·`accepted_by`를
기록한다. 같은 사용자가 같은 토큰으로 재시도하면 **같은 강아지의 200**을 되돌려주고, 다른
사용자는 404를 받는다. 만료된 초대는 **410 Gone**이다. 앱은 같은 요청을 재시도해 응답 유실
뒤의 성공을 복구하며, **목록으로 추측하지 않는다**(②).

근거: [수락 서비스](https://github.com/SAJOYO/DAENGS_dev/blob/1bf2d57f8947cc99496cca075b733551ecd606d0/backend/src/daengs_backend/services/pet_member.py),
[요청·응답 라우터](https://github.com/SAJOYO/DAENGS_dev/blob/1bf2d57f8947cc99496cca075b733551ecd606d0/backend/src/daengs_backend/routers/pet_member.py).

### 돌보미의 보행 촬영이 마지막 단계에서 막힌다

앱 `gait/HttpGaitAnalyzer.kt`는 티켓 → 영상 PUT → `confirm`을 연속 실행한다.
서버는 시작만 구성원에게 열고 `confirm_upload`는 대표만 허용한다. 따라서 돌보미는
영상 업로드 뒤 404를 받고 분석이 시작되지 않는다. 별도 확정 버튼 하나를 숨겨 해결할 수 없다.

서버는 `created_by`와 `can_confirm`·`can_delete`를 응답에 싣는다. 업로더 또는 대표가 확정할
수 있고 삭제는 대표만 가능하도록 합의했다. 앱은 `is_owner`로 다시 계산하지 않고 각 기록의
`can_*` 값을 따른다.

근거: [보행 시작·확정 서비스](https://github.com/SAJOYO/DAENGS_dev/blob/1bf2d57f8947cc99496cca075b733551ecd606d0/backend/src/daengs_backend/services/gait.py).

### 스크리닝 확정 권한과 삭제 버튼 판정 정보

서버 `confirm_record`는 창작자 전용이다. 기존 ②의 '스크리닝 확정은 대표 전용' 문구를
이 문서에서 바로잡았다. `ScreeningRun.kt`의 촬영 → 업로드 → 확정 흐름은 창작자인
돌보미에게도 열려 있어야 한다.

서버는 스크리닝 응답에도 `created_by`와 `can_confirm`·`can_delete`를 싣기로 했다. 확정은
창작자, 삭제는 창작자 또는 대표다. 앱은 새 기기에서도 이 값을 읽어 버튼을 정확히 가린다.

근거: [스크리닝 서비스](https://github.com/SAJOYO/DAENGS_dev/blob/1bf2d57f8947cc99496cca075b733551ecd606d0/backend/src/daengs_backend/services/screening.py),
[응답 스키마](https://github.com/SAJOYO/DAENGS_dev/blob/1bf2d57f8947cc99496cca075b733551ecd606d0/backend/src/daengs_backend/schemas/screening.py).

### 초대 취소가 문서에만 있다

서버는 대표 전용 초대 목록 조회와 `DELETE /app/pets/{id}/invites/{iid}`를 추가하기로 했다.
목록은 `id`·`expires_at`·`created_at`·`accepted_at`을 주고 평문 토큰은 다시 주지 않는다.
앱은 재시작·다른 기기에서도 활성 초대를 찾아 취소할 수 있지만 링크를 다시 만들 수는 없다.

근거: [구성원 라우터](https://github.com/SAJOYO/DAENGS_dev/blob/1bf2d57f8947cc99496cca075b733551ecd606d0/backend/src/daengs_backend/routers/pet_member.py),
[강아지 라우터](https://github.com/SAJOYO/DAENGS_dev/blob/1bf2d57f8947cc99496cca075b733551ecd606d0/backend/src/daengs_backend/routers/pet.py).

## ⑦ 화면 연결안 — 서버 계약 합의 후 구현

기존 홈·미니룸·마이·저장소 구조와 공통 Compose 컴포넌트를 이어 쓴다.

| 진입 | 표시·동작 | 상태 변화 뒤 |
| --- | --- | --- |
| 마이 → 강아지 카드 | 대표 보호자/돌보미 역할 표시, 프로필 읽기와 보호자 목록 진입. 수정·사진 변경·배웅·삭제는 대표만 | `Pet` 모델에 `is_owner`를 읽고 카드 클릭으로 수정에 우회 진입하지 못하게 처리 |
| 보호자 목록 | 대표 먼저, 본인 표시. 대표에게 초대·내보내기·대표 넘기기, 돌보미에게 나가기 | 서버 성공 후 강아지·보호자 목록 재조회 |
| 초대 만들기 | 유효 시간, 한 번 발급받은 링크 공유, 합의된 범위의 취소 | 공유창을 닫는 것을 초대 취소로 취급하지 않음 |
| 초대 링크 열기 | 로그인 필요 → 로그인 후 수락 화면 복귀 → 명시적 수락 → 결과 | URI 형식·호스트·앱 미설치 시 경로는 구현 전에 합의. 404 복구는 ⑥ 해결 필요 |
| 대표 넘기기 | 기존 돌보미 선택 → 대상 이름과 내가 돌보미로 남는다는 안내 → 확인 | `is_owner`와 `is_primary`를 별도로 재조회. 기존 초대는 무효화됨 |
| 내보내기/나가기 | 대상과 접근 종료 안내 → 확인 | 서버의 대체 대표 강아지 반영, 접근을 잃은 아이의 열린 화면·기존 요청 정리 |
| 저장소 → 케어 | 기록자 표시, 약 중복 확인, 작성자/대표만 삭제 | 약 확인은 같은 시각·`client_event_id`에 body `confirm=true`만 추가 |
| 강아지 삭제/회원 탈퇴 | 삭제 409는 돌보미 안내 후 쿼리 재확인. 탈퇴 409는 승계·내보내기 두 경로 | 실패 시 계정·강아지를 로컬에서 지우지 않음 |

**화면 진입뿐 아니라 앱 복귀 때도 새로 읽는다.** 현재 `MainActivity`의 강아지 조회는
세션 변화 중심이고 `ChatSummaryRoute`의 케어 조회는 화면 진입·선택 변화 중심이다.
다른 보호자가 기록·승계·내보내기를 한 뒤 같은 화면으로 복귀하는 경우를 추가해야 한다.
실패를 빈 목록·0건으로 바꾸지 않고, 계정·대상 변경 이전에 시작한 응답은 버린다.

**사진은 버튼뿐 아니라 자동 동기화도 확인한다.** `PetPhotoSync`는 도장 없는 로컬 사진을
업로드하도록 설계되어 있다. 대표 승계로 돌보미가 된 뒤 남은 사진이 자동 업로드되지 않도록
동기화 권한도 검사한다. 사진 조회 권한은 서버 계약과 별도로 대조한다.
